# LogServ App and AI Assistant Internals

This page describes how the LogServ App (`splunk_app_sap_logserv`) is built: its React architecture, the AI Assistant's architecture and implementation (file paths, type-system patterns, build mechanics, audit-event schemas, extension recipes), and the Environment Topology view. It is for engineers who maintain or extend the App.

For the customer-facing documentation, see the [AI Assistant section](../ai-assistant/overview.md). The customer-facing pages cover what users see and how to use the feature; this page covers how it's built.

!!! note "Build variant"
    The published v0.1.2 App artifact is the **full-LLM build** (`yarn build`), in which the free-form LLM path is present and governed at run time by the `templates_only_mode` setting (default off) — so everything here describing free-form dispatch (tool definitions, primers, Power Mode, tier sanitization on vendor calls) is live code, reached once a provider credential is configured. The compile-time **templates-only** variant (`yarn build:templates-only`) forces that setting on and leaves the same code present but unreachable — see **The Build Flag Pattern** below. The predefined-prompt path, MCP dispatch, tier sanitization of tool results, and the audit log are fully active in both.

## :material-circle-box:{ .taiconcolor } React App Architecture

The LogServ App is a custom React application, built with webpack (stack below). The Data TA's index-time pipeline (`props.conf` / `transforms.conf` routing, filtering and its Python handlers) does not depend on any UI code. The configuration pages of the Data TA and the Azure and GCP add-ons are generated by Splunk's UCC framework, which ships its own prebuilt React bundle in each add-on (`appserver/static/js/build/`, with its npm notices in `licenses.txt`). The Data TA's AWS S3 Direct screen is plain JavaScript.

**Stack:**

- **Build pipeline:** webpack-based bundle build atop `@splunk/webpack-configs`. Each Splunk app page resolves to a single React bundle. The build commands are in [Building the Packages from Source](build-from-source.md#build-the-logserv-app).
- **UI primitives:** `@splunk/react-ui` (forms, tables, modals), `@splunk/visualizations` (charts), `@xyflow/react` (Topology graph), `styled-components` for theming.
- **State management:** React context for cross-cutting concerns (AI Assistant, time range, refresh ticker); `useState` / `useReducer` for component-local state. No Redux.
- **Data fetching:** the custom `useSearch` hook wraps `@splunk/search-job` for SPL dispatches; it returns `results / loading / error` plus the search metadata the panel toolbar and Data Doctor consume (dispatched SPL, sid, effective time window, row count). Rollup-backed panels route windows under 90 minutes to a byte-equal raw query — see [Dashboard Data: Backfill and Freshness](../logserv-app/dashboard-data.md).
- **Routing:** React Router 7 with `HashRouter`, so URLs survive Splunk Web's app-namespace routing; the query string after the hash carries the time range (`?earliest=...&latest=...`).

The compile-time variant (the `TEMPLATES_ONLY` flag) is described under [The Build Flag Pattern](#the-build-flag-pattern-templates_only-and-future-flags), and the `[install] build` rule under [Splunk Static-Asset Cache Busting](#splunk-static-asset-cache-busting).

## :material-circle-box:{ .taiconcolor } AI Assistant Architecture

The AI Assistant is a chat-style panel in the LogServ App that lets analysts run predefined investigations and free-form prompts against their Splunk data. It has two distinct paths and one privacy invariant.

**Privacy invariant — enforced by the type system, not by policy:**

```
User question  -->  AI vendor  -->  AI picks tools  -->  MCP server  -->  Splunk
                       |                                       |
                       |  <----  Hidden<MCPToolResult>  <------+
                       |
                       v  (sanitize chokepoint: count + timing only — Tier 1)
                       |  (or aggregated metadata — Tier 2)
                       v
                  AI synthesizes narrative reply
```

Tool results from the Splunk MCP Server are typed `Hidden<MCPToolResult>`. The compiler refuses to put a `Hidden<T>` value into the outbound vendor payload; the only conversion is `sanitize(hidden, summarizer)`, which forces the caller to provide a summary string. No raw row and no unsummarized result reaches the vendor. What the summary may contain is set by the privacy tier:

- **Tier 1 (default)** — two numbers, a count and a timing. The AI sees no values; a model that writes its own queries can still make those numbers depend on event data, so a few bits per call can leak.
- **Tier 2 (admin opt-in)** — adds aggregated metadata: per-column cardinality, top-N values with counts for categorical columns, min/max/avg/sum for numeric columns, and the time range. No raw rows. Which names and values are sent in clear is set by the rules described under the brand type pattern below.
- **Tier 0 (Ollama)** — not implemented in this release. A tier-0 setting uses the Tier 1 summary, and the `ollama` provider falls back to the mock provider, which calls no vendor. Do not select either.

In every tier, a tool call that **fails** reaches the vendor only as its HTTP status and a fixed error class, never as Splunk's or the MCP server's error text; see **Failed calls and refusals** below and [Privacy Tiers](../ai-assistant/privacy-tiers.md#failed-tool-calls-every-tier).

**Two paths:**

- **Predefined prompts (no LLM call):** the user opens the prompt browser and clicks one of the cataloged prompts. The orchestrator dispatches the saved search through the Splunk MCP Server, renders the result tile in the right pane, and appends a static interpretation and suggested-next-steps card. **No vendor LLM is invoked.** This is the only path in the templates-only build.
- **Free-form prompts (LLM-driven):** the user types a natural-language question. The orchestrator sends the system primer, the user message and the tool definitions to the active vendor (Anthropic, OpenAI, Azure OpenAI or AWS Bedrock). The vendor picks tools, the orchestrator dispatches them in parallel through MCP, the vendor sees only the privacy-tier summary, and the vendor writes the reply.

**Audit log:** AI Assistant actions on both paths produce audit events in the `logserv_ai_assistant_audit` index; [Audit Event Schemas](#audit-event-schemas) lists the categories and their fields. The browser writes each event as the signed-in user, so a user whose role lacks `edit_tcp` and `edit_log_alert_event` is not audited (see [Who Can Write Audit Events](../ai-assistant/audit-log.md#who-can-write-audit-events)). The Audit Log tab in Settings is an in-app viewer, and an optional HEC forwarder sends a copy of each event to a separate Splunk or SIEM destination.

**Splunk MCP Server prerequisite:** [Splunk MCP Server (Splunkbase App 7931)](https://splunkbase.splunk.com/app/7931) v1.1.0 or later, installed on the same search head as the LogServ App: the predefined prompts run through its Run Saved Search tool, which first shipped in 1.1.0. Version 1.2.1 or later is recommended (SVD-2026-1004). The App's health check (`MIN_MCP_SERVER_VERSION` in `components/ai/mcp/versionGate.ts`) refuses only versions below 1.0.3, the CVE-2026-20205 fix, and has no upper bound. Cookie auth from the same Splunk Web session works by default; an optional bearer token can be configured for OAuth-strict environments. See [Splunk MCP Setup](../ai-assistant/mcp-setup.md).

## :material-circle-box:{ .taiconcolor } Environment Topology Architecture

The Environment Topology view (route `#/topology/integration-topology`) is a graph of SAP systems, integration partners and endpoints across the SAP landscape, implemented as a React component on top of `@xyflow/react`.

**Data sources:** the view reads KV Store collections that scheduled searches in `default/savedsearches.conf` fill from the existing sourcetypes (no new ingest required); it runs no raw search for the graph itself.

| Saved search | Schedule (cron, server time) | Writes | Reads |
|---|---|---|---|
| `logserv_topology_aggregate_nodes` | `5 * * * *` | `logserv_topology_nodes` (per-hour node activity) | `sap:abap:gateway`, `sap:abap:icm`, `sap:hana:audit`, `sap:hana:tracelogs`, `sap:saprouter`, `sap:webdispatcher:access`, and the `host` of any event that carries `sap_sid` |
| `logserv_topology_aggregate_edges` | `6 * * * *` | `logserv_topology_edges` (per-hour edges with per-type aggregates: HTTP latency, HANA tenant command durations, HANA audit success / failure, RFC gateway connections in the direction they were made, SAP Router `CONNECT TO` targets with their failed connections; loopback targets 127.0.0.0/8 excluded) | `sap:abap:gateway`, `sap:hana:audit`, `sap:hana:tracelogs`, `sap:saprouter`, `sap:webdispatcher:access` |
| `logserv_topology_aggregate_inventory` | `7 * * * *` | `logserv_topology_inventory` (IP / host to SID) | `sap:abap:gateway`, `sap:abap:icm`, `sap:hana:tracelogs`, `sap:saprouter`, and the `host` of any event that carries `sap_sid`; Web Dispatcher events are left out |
| `logserv_topology_detail_aggregate` | `8 * * * *` | `logserv_topology_detail_rollup` (read by the right-pane detail tabs) | every sourcetype in `sap_logserv_logs` (the per-host and per-SID / IP counts and the errors); `sap:abap:gateway`, `sap:abap:icm`, `sap:hana:audit`, `sap:hana:tracelogs`, `sap:saprouter`, `sap:webdispatcher:access` (the per-type tabs) |
| `logserv_topology_enrichment_aggregate` | `32 2 * * *` (last 30 days) | `logserv_topology_ip_enrichment` (host and user names per IP address) | `sap:hana:audit`, `XmlWinEventLog` (EventCode 4624), `sap:sapstartsrv`, sshd lines in `linux_messages_syslog` / `linux_secure` |

Each has a `logserv_topology_*backfill*` twin that **Settings > Dashboard Data** runs.

**Self-derived IP→SID inventory:**

The "which IP belongs to which SID" mapping is derived from a multi-source `union` SPL that counts the events each SAP SID logged for an IP address or host: the endpoint is attributed to its most recent SID (of the SIDs seen in its most recent hour, the one with the most events), so a host that really runs two systems at once is shown under the one that logged more; an exact tie keeps the previous attribution, and an endpoint never attributed is surfaced as "unknown". Resolution depends on what your data exposes: unique hostname/IP appearances across multiple SAP sourcetypes (HANA tracelogs, ABAP gateway L=, ICM local IPs, SAP Router `sapms<SID>` targets, and the `host` of any event that carries a SID) attribute cleanly, while shared NAT IPs and external partners typically remain unknown. A Web Dispatcher's own logs (its access log and its ICM trace) are not an attribution source; see [Environment Topology](../logserv-app/dashboards/topology.md). Additional inventory sources can be added by appending another `union` arm — the inventory framework is extensible per-customer without new ingest.

**Saved layouts:**

User-arranged graph layouts are persisted via Splunk KV Store collection `logserv_topology_layouts`. The schema (currently v5) carries the layout mode (Force / Layered / Tree), node positions, panel state, viewport zoom + pan, enabled integration types and the types the view offered when the layout was saved (so a type added later starts enabled), selected node and edge, active right-sidebar tab, and snap mode. Layouts are saved per user under a name, and each user can mark one per layout mode as the default that loads automatically. A layout saved in an older schema does not load; save it again.

**Data refresh:**

The view re-reads the KV Store on initial mount, on a change of the global time range, and whenever the user clicks the toolbar's **Refresh** button. There is no auto-polling: the hourly schedules govern data freshness, so the graph and the detail tabs are hourly-fresh, like the dashboards.

**Design history:** an earlier design ran six SPL searches on demand every time the view opened, which produced a 5-15 second page load on busy Splunk instances; the data layer was rewritten to the KV Store design above. An earlier Live | Lookup toggle polled every 30 seconds, a leftover of that on-demand design; it was removed once the data moved to hourly KV Store aggregation, because about 119 of every 120 ticks returned identical data. The Layered and Tree layout modes (`layoutLayered.ts`, `layoutMrtree.ts`, each imported on demand) load the same lazy elkjs chunk (`elkjs-bundled`), fetched only when a Layered or Tree layout is first picked, so Tree mode added no second copy of elkjs; Force mode loads neither.

## :material-circle-box:{ .taiconcolor } The `Hidden<T>` / `Visible<T>` Brand Type Pattern

The privacy invariant — *"no raw event and no unsummarized tool result is ever transmitted to any AI vendor; only the active tier's summary is"* — is mechanically enforced via TypeScript brand types split across `components/ai/types/Hidden.ts` and `components/ai/types/Visible.ts`:

```typescript
// components/ai/types/Hidden.ts
declare const HIDDEN_BRAND: unique symbol;
export type Hidden<T> = T & { readonly [HIDDEN_BRAND]: true };
export const markHidden = <T>(v: T): Hidden<T> => v as Hidden<T>;
export const unwrapHidden = <T>(v: Hidden<T>): T => v;

// components/ai/types/Visible.ts
declare const VISIBLE_BRAND: unique symbol;
export type Visible<T> = T & { readonly [VISIBLE_BRAND]: true };
export const markVisible = <T>(v: T): Visible<T> => v as Visible<T>;
export const unwrapVisible = <T>(v: Visible<T>): T => v;

export const sanitize = <T>(
    hidden: Hidden<T>,
    summarizer: (value: T) => string,
): Visible<string> => {
    const inner = unwrapHidden(hidden);
    const summary = summarizer(inner);
    return markVisible(summary);
};
```

**Invariant:** the only way to obtain a `Visible<string>` from a `Hidden<T>` is via `sanitize(hidden, summarizer)`, whose return type is locked to `string` so a summarizer cannot pass the result object through. The compiler refuses any other coercion path. The summarizer receives the unwrapped data and returns a summary string; the orchestrator's call site picks the summarizer based on the active privacy tier (`tier1Summary` for Tier 1, `tier2Summary` for Tier 2). The type system cannot see what text the summarizer copies into that string, so the summarizers themselves are the place to audit: `tier1Summary` writes two numbers, and `tier2Summary` writes aggregates under the rules of `utils/vendorColumnText.ts` (below).

**Where the chokepoint runs:** `useAIAssistant.ts` `sendUserMessage` → tool dispatch → `MCPClient` returns `Hidden<MCPToolResult>` → `sanitize(toolResult, tier === 2 ? tier2Summary : tier1Summary)` → resulting `Visible<string>` is appended to the outbound vendor message buffer.

**Where the type system enforces:** every outbound vendor message is built from `Visible<Message>[]`. Anywhere code constructs an outbound message, the types refuse a `Hidden<T>` value. There is no `as any` cast; bypassing requires modifying the brand-type code itself, which is reviewed.

**Failed calls and refusals — no Splunk or MCP text, in any tier.** A type cannot tell error text from data, so the summarizers do not pass it on. When `detectToolError(inner)` finds an error in a result, `tier1Summary` and `tier2Summary` both return `wrapAsToolResultData(vendorToolErrorText(detected))` — `Tool error (HTTP <status>, class=<class>): <fixed hint> The error text is shown to the user only.`, with `HTTP <status>, ` left out when the status is not an integer from 100 to 599. The class is one of `parse_error`, `unknown_command`, `missing_lookup`, `missing_saved_search`, `permission`, `timeout`, `rate_limited`, `not_found`, `server_error`, `other`: fixed regexes over the first 2,000 characters of the message pick it, first match wins, and the status decides when none matches (401/403 `permission`, 404/410 `not_found`, 408/504 `timeout`, 429 `rate_limited`, 5xx `server_error`, else `other`). The message only selects which fixed string is returned; no part of it is sent: a Splunk error repeats the failed search, into which a subsearch can put event text. The full message stays in the `Hidden` result, so `ToolResultPanel` still shows it to the user; the audit events never carried it.

The three refusals the hook makes before dispatch — the session tool-call cap, `vetToolCall` (saved search outside the catalog, undeclared tool) and `vetAdHocQuery` (the SPL guard: the denylist, the allow-list and the search-parser check) — build their vendor summary at the refusal site: `sanitize(syntheticHidden, () => wrapAsToolResultData(vendorRefusalText(reason)))`, with the reason the hook just wrote (`capReason`, `toolVerdict.reason`, `guardReason`). `vendorRefusalText` prefixes `Tool call refused by the App before it ran: `, turns control characters other than tab, LF and CR into spaces, replaces `<TOOL_RESULT_DATA>` tags with `<filtered>`, and caps the reason at 1,000 characters. It is never applied to a server result, so a server message that imitates a refusal is classified like any other error. Numbers still reach the vendor: a count and a timing on every successful call (Tier 1 and 2), the HTTP status and fixed class on a failed one, and the `is_error` flag where the wire format has one (Anthropic and Bedrock). In Tier 1 the count is `found.length`, where `found = extractRowsForSummary(inner)` — the same result rows Tier 2 counts, so an empty `results: []` gives `Returned 0 rows` — and `countRows(inner.content)` only when `found === null` (no row shape: the length of the `content` array, or `totalRowCount`). The timing is `inner.executionMs`, else the time the browser measured. Tier 1 therefore limits bandwidth rather than making leakage zero: a model writing its own queries can make the timing, the failure and its class, and the count depend on event data, so a few bits per call can leak — up to about log2 of the largest count the server can return through the count (the row limit, or the server's total for `totalRowCount`). The session tool-call cap (`tool_calls_per_session_cap`, default 100) limits the calls per chat session; the counter resets when the chat is cleared (the message list becomes empty), and `0` turns the cap off.

**Tier 2 — `vendorColumnLines`.** `tier2Summary(inner, fallbackMs, topN, piiOpts, onRedaction, authorTexts)` computes `const found = extractRowsForSummary(inner)`. `extractRowsForSummary` tries, in order, `structuredContent.results`, the JSON of `content[0].text` (its `.results`, or the parsed array), a `content` array and `content.rows`. It returns `null` when none is there, and also for a `content` array that holds an MCP content block (`isMcpContentBlock`: a `type` of `text`, `image`, `audio`, `resource` or `resource_link` with a `text`, `data`, `resource` or `uri` key), so reply text is never taken for a row. With `found === null` Tier 2 sends only `Returned a result that is not in row form, in ${ms}ms.`; with no rows, `Returned 0 rows in ${ms}ms (no events matched the query in the selected time range).`; otherwise `Returned ${found.length} rows in ${ms}ms.` followed by exactly the lines `vendorColumnLines(found, { topN, sanitizeValue: sanitizeAggregateValue, piiOpts, onRedaction, author: buildAuthorContext(authorTexts) })` returns. It reads no column name and no `_time` itself. The dispatcher builds `authorTexts`, the text the model or the App wrote for the call: `[mcpArgs.query]` for `splunk_run_query` (`[]` when the query is not a string); `[SAVED_SEARCH_SPL[name]]` for a saved search in the catalog (an own-property check); otherwise `CATALOG_SPLS`, the SPL of every intent-map prompt. The author text only decides names and how values are traced, and is never echoed. The rules, in `utils/vendorColumnText.ts`:

- **Author context** (`buildAuthorContext(texts)` → `{ words, quotedAliases, readings }`). Each text, cut at `MAX_QUERY_CHARS` (20,000), gives `words` — every match of `NAME_WORD_RE` (`[A-Za-z0-9_]+`) in the whole text, quoted parts included — `quotedAliases`, every double- or single-quoted token that directly follows the word `AS` (any case), unquoted, and a *reading*. The reading tokenizes the text (double-quoted and backquoted text as single tokens; a single-quoted token only when it holds no `|`, bracket, double quote or line break, so a stray apostrophe is one character and cannot hide the pipes after it; words of `[A-Za-z_][A-Za-z0-9_.:-]*`; single characters), splits it into commands at pipes outside brackets, and reads it command by command (`readPipeline` → `readCommand`) into a `FieldState`: an `env` of `ColumnTrace`s by name, wildcard patterns, and a default for any other name: a raw field traced to itself, until a command that rebuilds the result (`stats`, `tstats`, `chart`, `timechart`, `top`, `rare`, `xyseries`, `untable`, `transpose`, `fieldsummary`) replaces it — with nothing, or with the pivot-cell or mixed trace. The first command needs no pipe: a known command name is read as that command, anything else (a macro included) as the implicit search. A text longer than `MAX_QUERY_CHARS`, more than `MAX_TRACE_COMMANDS` (256) commands across the text and its subsearches, or a subsearch deeper than `MAX_SUBSEARCH_DEPTH` (8), or more than `MAX_WILDCARD_PATTERNS` (12) wildcard definitions in one text (each resolves through the ones before it, 2^k per column), makes every column untraced (`opaqueAll`). The first command inside `appendpipe […]` is always read as a command (`readPipeline(…, firstIsCommand)`), never as the implicit search.
- **Names** (`planVendorColumns` → `isSendableColumnName(name, author)`). A name is sent when it is in `FIXED_COLUMN_NAMES` (`count`, `percent`, `total`, `Total`, `NULL`, `OTHER`, `column`, `sum`, `avg`, `min`, `max`, `dc`, `values`, `earliest`, `latest`, `first`, `last`, `median`, `mode`, `stdev`, `range`, `rate`, `field`, `distinct_count`, `is_exact`, `numeric_count`, `mean`), or when `isNameShaped(name)` — at most `MAX_NAME_CHARS` (40) characters and `FIELD_NAME_RE` (`^[A-Za-z_][A-Za-z0-9_.:-]{0,39}$`) or `FUNCTION_NAME_RE` (one call over a field-name-shaped argument, `*` or nothing) — and every word of `nameWords(name)` is in `author.words`: whole words, exact case — or the name is in `author.quotedAliases`, at most 40 characters and matches `QUOTED_ALIAS_RE` (`^[A-Za-z_][A-Za-z0-9_.:-]*(?: [A-Za-z0-9_.:-]+)*$`: words separated by single spaces), with every word in `author.words`. Either way `sanitizeAggregateValue` must return the name unchanged. Any other name becomes `col_N` (N = 1-based position among the result's columns that do not start with `_`), and the summary adds `withheldNote(K)` (`Column names withheld: K. Each such column is shown as col_N, …`). Naming does not depend on the redaction setting. So `sum(jsmith)` (from `timechart count by user | stats sum(*)`) is `col_N` unless the author text has the word `jsmith`, and `username` is `col_N` when the author text has only `user`.
- **Traces** (`traceColumn(name, author)` → `ColumnTrace { traced, count, cell, mixed, fields, why }`, merged over every reading that outputs the column; a column no reading outputs is untraced, with every word of the author text as its fields). TRACED only through: the field itself (raw, lookup, `by` / `over`, `top` / `rare`, `table` / `fields`); a statistics function (`STAT_FUNCTIONS`) over one field, nested included (`latest(values(user))` → `user`, or the column named `values(user)` when one exists), with or without `AS`; `field AS alias`; a rename without wildcards (the source name is deleted); `eval x=<one bare [A-Za-z_]\w* field or one single-quoted ref>`, assignments read left to right as Splunk evaluates them; `lookup … OUTPUT f [AS a]` (`OUTPUTNEW` merges with the existing definition) — an output that echoes a match field (`lookupField [AS eventField]` before `OUTPUT`) is that event field's trace; any other output is `{ traced, fields: [f, …the match fields' fields] }`, traced only when every match field is, so a mapping keyed on an identifier is an identifier; `CURATED_LOOKUP_OUTPUTS` (the category, source and date of the App's threat-intel lookups) keep `baseTrace(f)`; and counts — `COUNT_TRACE`, no fields: `c` and `count` bare or as a call, `count(eval(…))` included, and `dc`, `distinct_count`, `estdc` or `estdc_error` over ONE traced, unmixed field (over a computed field it is untraced, with that field's fields); `top` / `rare`'s `count` and `percent` (or `countfield` / `percentfield`; a positional limit, `top 10 uri`, is skipped like `limit=10`); `fieldsummary`'s `count`, `distinct_count`, `numeric_count` and `is_exact`; `transaction`'s `eventcount`, `linecount`, `closed_txn` and `field_match_sum`. UNTRACED, each with a `why`: any other eval expression (its `fields`: the words outside double quotes, also split on `.`, `:` and `-`, the contents of single quotes, and what each resolves to, plus the words of its double-quoted literals as they are; a macro in it reads every word of the text); `rex` (named groups `(?<n>)`, `(?P<n>)` and `(?'n')`, `mode=sed`, `offset_field`; the words of the pattern join the fields, and a group merges with the earlier definition of its name — rex sets it only where it matches), `spath` (the words of the path and output join the fields; the output merges with its earlier definition), `fieldformat` (untraced, merged with the column's earlier definition), `strcat`, `bin` / `bucket`, `convert`, `iplocation`, `transaction`'s `duration`, `addtotals` / `addcoltotals`; wildcard `rename` / `AS` and wildcard aggregations (patterns); a dynamic `{x}=` eval target; the split cells of `chart` / `timechart` / `xyseries` (`cell: true`); `transpose`, `untable` and `fieldsummary` (`mixed: true`); two different definitions of one name (`mergeTraces`; two counts stay a count); a column an `append` / `appendcols` / `join` / `union` / `multisearch` / `set` / `appendpipe` subsearch defines (`mergeSub`: a field passed through by its own name stays traced; `search` / `where` subsearches are not read and add nothing); a field read where it no longer exists (`sourceOf`). `opaqueAll` — every column untraced, its `fields` every word of the text — for `lookup` without `OUTPUT`, `inputlookup` after the first command, `foreach`, `map`, any unknown command, a macro as a piped command, and an `eval`, `rename`, `stats`, `chart`, `top`, … the reader cannot split. An untraced definition that lists more than `MAX_SOURCE_STEPS` (64) fields lists every word of the text instead. Every limit fails closed.
- **Value rule** (`columnValueRule(name, author, piiOpts)` → `{ trace, identifier, textSafe, numericIdentifier }`). `identifier` is true when `isIdentifierColumnName` holds for the column's own name or any of `trace.fields` — the class table of `fieldClassification.ts` (identifier and address; host when hostnames are redacted), the `piiRedaction` name patterns (hostnames when they are redacted) plus `id`, `uid`, `gid`, `guid`, `uuid`, `pid`, `ssn`, `iban`, `phone`, `msisdn`, `imsi`, `imei`, `acct` and account / card / employee / personnel numbers, as the whole name or after `_ . : -`, case-insensitive, and camelCase `…Id` / `…ID`. `textSafe` is `traced && !count && !cell && !mixed && !identifier`; `numericIdentifier` is `!count && (identifier || mixed)`.
- **Columns** past the first 30 are reported only as `R more columns not summarized.`.
- **Numeric values** (`numericDisclosure(named, columnValueRule(…).numericIdentifier, distinct, piiOpts)`). With PII redaction on, a numeric identifier column sends `values withheld` at any cardinality (`withheld-identifier`); a column with one distinct value that is not named or is a numeric identifier sends `values withheld` at any redaction setting; any other numeric column sends min / max / avg / sum, untraced ones and columns shown as `col_N` included.
- **Time** (`vendorTimeRangeLine`). Every non-null `_time` must parse (`parseVendorTime`: an epoch in seconds as a number or digit string, 0 to 2100-01-01, or a strict ISO-8601 timestamp with `Z` / `+hh:mm` / `+hhmm` on a real calendar date); the line is then `Time range: <ISO UTC> → <ISO UTC> (UTC).` built with `new Date(ms).toISOString()` — no zone from the data is sent — else `Time range: not shown (the _time values are not all timestamps).`. A parsed range is sent only when `timeRangeAllowed(author)`: `_time` traced, not a count, cell or mix, every field in `TIME_SOURCE_FIELDS` (`_time`, `bucket_ts`, `day_ts`); otherwise `TIME_NOT_SHOWN_COMPUTED` (`Time range: not shown (the query computes _time from other fields).`).
- **Categorical values**: top-N by count, `sanitizeAggregateValue`, then — with PII redaction on, unless the column is named and `textSafe` — `redactValueIfPII(PII_STAND_IN_COLUMN, …)` (`user`), so every non-empty value that is not `<filtered>` becomes a `<redacted-…>` tag; then 40 characters each, within a 160-character line. A named, traced column whose name and source fields mark no identifier keeps its values; with redaction off every column keeps them.
- **`onRedaction`** (the audit's `tier2RedactionsApplied`) fires for each value redacted and for each numeric column withheld as `withheld-identifier` (an identifier field, or mixed values). A withheld name does not fire it.

What this does not close: Tier 2 sends aggregated event values by design. A column shown as `col_N` or untraced keeps its numeric statistics unless it is a numeric identifier, and a named, traced column whose name and source fields mark no identifier — an event field, a lookup column not keyed on an identifier, `eval m=_raw` included — is sent, filtered and cut to 40 characters. Counts are not traced to the fields that shaped them, so a count can carry a few bits a query manufactures (`stats count by <a computed multivalue>` then `stats count`); documented, not closed. A name made only of words the model wrote is model-authored text and is sent even when it equals a value the model has seen (`… as jsmith`, or `jsmith` typed anywhere in its query); the catalog's words have the same property. Name-based PII redaction is hygiene for ordinary queries, not a content filter.

**Augmenting a `Visible<T>`-branded string:** direct concatenation produces a TS error since the brand type can't widen back automatically. The pattern is `unwrapVisible() + new string + markVisible()`. The Power Mode primer augmentation uses this pattern.

## :material-circle-box:{ .taiconcolor } The Build Flag Pattern (`TEMPLATES_ONLY` and Future Flags)

### How the flag disables the LLM path

`TEMPLATES_ONLY` is baked into the bundle at build time (webpack DefinePlugin) and cannot be changed post-deploy. Rather than duplicating a guard at every consumer, the flag **forces the runtime `templates_only_mode` value on** at the config-read chokepoint:

1. **`utils/aiConfigApi.ts`** — the enforcement point. The flag is OR-ed into `templates_only_mode` inside `parseRawContent` (the single normalizer for BOTH the KV Store row and the conf stanza) and into `DEFAULT_AI_CONFIG` (the both-reads-failed fallback), so EVERY read path reports `templates_only_mode: true` regardless of what is stored. This is what defeats a stored KV row of `0` carried over from a full-LLM install.
2. **`hooks/useAIAssistant.ts`** — ORs the flag into the `sendUserMessage` guard as prop-chain-independent defense in depth; a dispatch attempt short-circuits with a system notice directing the user to the prompt browser.
3. **`state/AIAssistantConfig.ts`** — forces the pre-load default, so the UI never renders an LLM-enabled state while config is still loading.
4. **`bin/build.js`** — patches the STAGED conf default to `true` so the artifact is self-describing (cosmetic; the webapp force is the gate).

**What the flag does NOT do:** the vendor provider modules (`AnthropicProvider.ts`, `OpenAIProvider.ts`, `AzureOpenAIProvider.ts`, `BedrockProvider.ts`) remain in the bundle, and their endpoint strings remain visible in `home.js`. Bundle-level stripping was explicitly declined — this is a **functional disable**, not a code strip. For policy-driven deployments where the LLM code must be physically absent from the artifact, use the frozen v0.0.6 line, which deletes the provider implementations from source instead.

### Single source of truth

`buildFlags.ts` is the canonical module for compile-time values — it exports each flag as a typed boolean derived from a build-time substitution. Use sites import the flag from `buildFlags.ts` rather than reading the underlying env var directly. The two build variants of the same build number differ in exactly two bundle regions — the compiled flag module and styled-components' per-build salt — and that byte-diff is the proof the full-LLM build is otherwise unchanged.

## :material-circle-box:{ .taiconcolor } The Chat Citation Parser

`components/ai/chat/ChatMessage.tsx` parses inline markers in assistant_text + guidance messages. The regex:

```typescript
const TEXT_PATTERN = /\[(?:→|->)\s*([a-zA-Z0-9_:.\-]+)\]|\[severity:(critical|high|medium|low)\]|\*\*([^*]+)\*\*/g;
```

Three numbered capture groups disambiguate which alternative fired:

| Group | Pattern | Renders as |
|---|---|---|
| 1 | `[→ logserv_xxx]` or `[-> logserv_xxx]` | Clickable scroll-to-tile span via `onJumpToResult(toolUseId)`; auto-appends sibling `↗ Dashboard` chip(s) + `↗ Run SPL` chip |
| 2 | `[severity:critical|high|medium|low]` | Glossy colored dot via `<SeverityDot $level={level} />` |
| 3 | `**bold text**` | Bold-stripped: the `**` markers are dropped and the inner text is re-parsed recursively for nested citation / severity markers |

**The recursive parse:** when the AI drifts and emits `**[severity:medium]**` (markdown bold wrapping the severity marker), the bold alternative matches first and would render the inner text as plain string, losing the severity dot. The fix recursively calls `renderTextWithCitations()` on the bold inner content. Save/restore of `TEXT_PATTERN.lastIndex` around the recursive call is required because the regex is module-scoped + `/g`-stateful — not saving would corrupt the outer iteration.

**Why module-scoped state:** `lastIndex` reset at function entry handles the common case. For recursive parses, save/restore around the call is required.

**Alternatives considered for the bold-wrapped severity marker:** re-ordering the regex alternatives so severity matches first doesn't help — bold wraps around the severity, so even if severity tries first, it can't match inside an unmatched bold span. Updating the primer to forbid bold around severity markers helps future prompts but doesn't repair existing UI; the parser must be tolerant either way.

## :material-circle-box:{ .taiconcolor } The MCP Tool Definitions Sent on Every Free-Form Request

The AI sees these two tool definitions on every free-form request. The source of truth is `DEFAULT_TOOLS` in `hooks/useAIAssistant.ts` (TypeScript field `inputSchema`); the definitions are sent as the request's top-level `tools` array — the primer separately teaches the AI when to use each. The block below shows the **Anthropic wire form** (`input_schema`; the OpenAI/Azure path maps the same schema to `function.parameters`):

### `splunk_run_saved_search`

```json
{
    "name": "splunk_run_saved_search",
    "description": "Dispatch a saved search from the LogServ App's catalog.",
    "input_schema": {
        "type": "object",
        "properties": {
            "name": {"type": "string", "description": "Saved-search name from the catalog (e.g., logserv_hana_failed_auth_24h)"},
            "earliest_time": {"type": "string", "description": "Splunk earliest token (-24h, -7d, etc.)"},
            "latest_time": {"type": "string", "description": "Splunk latest token (now, etc.)"},
            "render_hint": {"type": "string", "enum": ["table", "timechart", "kpi", "pie"]},
            "top_n": {"type": "integer", "minimum": 1, "maximum": 50, "description": "Width of categorical aggregates the AI receives in Tier 2 summary. Default 10."}
        },
        "required": ["name"]
    }
}
```

The schema carries no `enum` of names: the catalog reaches the AI as primer text, and the name is checked at run time.

**How a saved-search call is dispatched.** Every `splunk_run_saved_search` call — a predefined prompt from the prompt browser and a free-form tool call alike — goes through `MCPClient.runSavedSearch`, the single choke point:

- **Allow-list.** The allowed names are the saved-search names in `logserv_intent_map.json` (the 48 read-only prompts and the 13 ES correlation searches); `useAIAssistant.ts` builds the set from the intent map it already imports, so the allow-list, the primer catalog and the prompt browser cannot drift apart. The match is exact and case-sensitive. `buildAllowedSavedSearches` returns a frozen `ReadonlySet<string>` view over a private copy of the names: it has no `add`, `delete` or `clear` (a cast does not help — they are not functions), `Set.prototype.add.call` on it throws, and its members cannot be replaced, so no code that holds the list can widen it. Every rollup aggregation, retention, backfill and ES feed is outside it, so the AI cannot run one.
- **Explicit arguments.** `buildSavedSearchArgs` builds the MCP arguments field by field from the vetted name (`saved_search_name`), the App (`app` = `splunk_app_sap_logserv`, so the server runs this App's search and not a same-named one elsewhere) and the time range (`earliest_time` / `latest_time`); the model's `arguments` object is no longer spread into them, so it cannot replace `saved_search_name` or add keys.
- **Refusal.** A name outside the allow-list is refused before any MCP request. For a free-form tool call, `vetToolCall` in the tool loop refuses it before the call reaches `runSavedSearch`: the AI receives a synthetic error tool_result, and a `security_blocked_spl` audit event records `spl` = `(saved search) <name>` with `operator` = `saved_search_not_in_catalog`. The choke point itself only returns the isError result; predefined prompts take their names from the intent map, and the allow-list consistency suite checks that every one of them is allowed.
- **Unknown tools.** Only the two tools in `DISPATCHABLE_TOOLS` (the two offered in `DEFAULT_TOOLS`) are dispatched; `vetToolCall` refuses any other tool name the model emits instead of forwarding it to the MCP server, with a `security_blocked_spl` audit event (`spl` = `(tool) <name>`, `operator` = `tool_not_declared`).

### `splunk_run_query`

Same schema shape but accepts a `query` (SPL string) instead of `name`. Before dispatch the hook awaits `vetAdHocQuery(adHocQuery, { user: ctx.user, signal: controller.signal })` (`components/ai/splParserCheck.ts`; a `query` that is not a string is checked as the empty query, and refused): the denylist, the allow-list, then Splunk's search parser. Any refusal is recorded, sent to the vendor as the App's reason, and the query is never dispatched.

## :material-circle-box:{ .taiconcolor } The SPL Static-Analysis Guard

`utils/splGuard.ts` has two fences. The first, `analyzeSpl(spl: string): { blocked: boolean; reason?: string; operator?: string }`, is a **denylist**: it refuses a known list of risky commands — Splunk's own, with every alias Splunk declares for them (checked against `system/default/searchbnf.conf` of Splunk 9.4.3), and a few named third-party ones — and passes every other command. The second, the allow-list (`analyzeAdHocSpl`, below), refuses every command, lookup and data source that is not on its lists, so another installed app's custom commands and external lookups are refused even when the denylist does not name them. The denylist refuses a query at the first of seven checks that fails, in this order:

1. **Inline comment** (`operator` = `inline_comment`) — three backticks anywhere. Splunk drops a comment before it runs the search, so a comment placed inside a word (`saved` + comment + `search`, or between `|` and `outputlookup`) would hide that word from the checks below. Any comment is refused rather than stripped.
2. **Unmatched backtick** (`unbalanced_backtick`) — an odd number of backticks, so a macro reference cannot be left open.
3. **Ambiguous quoting** — a double quote that is never closed (`unterminated_quote`), or a backslash-escaped double quote outside a quoted string (`escaped_quote`). Either would make the guard's idea of what is quoted differ from Splunk's. From here on, checks 4 and 6 read the copy that `blankQuotedStrings(query)` returns: the content of every double-quoted string replaced by spaces, backslash escapes inside a string honoured (`\"` and `\\` do not end it), the quote characters and the length kept. Quoted text then cannot fake a command position (`"[DELETE]"`, `"(?<tag>[AI])"`). Only double quotes are blanked: a `|` or `[` inside single quotes counts as a command position, which only ever refuses more. Every check that a word split by quotes could dodge also reads a second copy, `dequoted`: the query with every quote character, double and single, removed and the quoted content kept (`"saved"search` reads as `savedsearch`, `'in'to` as `into`). Splunk may or may not join such pieces into one word; the guard assumes it does and fails closed.
4. **Forbidden command or word** (`operator` = the matched name, lower-cased):

    ```typescript
    export const FORBIDDEN_SPL_COMMANDS = [
        'collect', 'stash', 'summaryindex', 'sumindex',
        'mcollect', 'meventcollect',
        'outputlookup', 'outputcsv', 'outputtext',
        'delete',
        'sendalert', 'sendemail',
        'script', 'run', 'runshellscript',
        'dump', 'tscollect', 'createrss',
        'rest', 'outputtelemetry',
        'curl', 'wget', 'sendresults',
        'ai', 'deletemodel',
        'macro', 'savedsplunk',
        'map',
    ] as const;

    export const FORBIDDEN_SPL_WORDS = ['savedsearch', 'savedsplunk'] as const;
    ```

    (The source lists them one per line, each with a comment and, for Splunk's own commands, its `searchbnf.conf` line; `map` stays last because the build gate reads the list.) A command is matched at command position on the quote-blanked copy; a word anywhere in the raw query, quoted text included, and then anywhere in `dequoted` (`| "saved"search X`, `| from "saved"search:X`). A command word written with double or single quotes in it (`| "delete"`, `| de"lete"`, `| de'lete'`) is refused as well: at each command position of the blanked copy the guard reads the word from the raw query, removes its quote characters, and refuses it when it starts with a forbidden command or a forbidden word (`| sav"edsearch" X`), reporting that name as the operator. `macro` is refused at command position only, because it is a common word.

5. **External lookup** (`external_lookup`) — `EXTERNAL_LOOKUPS` = `['dnslookup']`, Splunk's own external lookup (`system/default/transforms.conf`, `external_cmd = external_lookup.py clienthost clientip`). Each row is a DNS query, so a value built into a host name reaches the domain's name server. Refused as a word anywhere in the raw query or in `dequoted`: `lookup dnslookup ...`, a quoted name, a name split by quotes (`"dns"lookup`), the eval `lookup()` function. Every other lookup, the App's included, passes.
6. **MLTK `fit ... into`** (`fit_into`, `fitThenInto`) — `fit ... into` saves or overwrites a model. At each command position of the blanked copy, the command word counts as `fit` when the blanked text there starts with `fit`, (`fit"a"`), or the raw word with its quote characters removed does (`"fit"`, `f'it'`). From the first such position, the query is refused when the word `into` appears anywhere up to the END of the query, in that remainder with its quote characters removed (`"in"to`) or turned into spaces (`"a"into`). The scan does not stop at the next `|` or `]`, because either may sit inside a single-quoted field name (`'a|b'`), and quoted text counts. `fit` with no `into` after it, and `apply`, only read and stay allowed.
7. **Macro** (`macro`) — every backtick pair must reference one of `ALLOWED_SPL_MACROS`, the stanza names of the App's `default/macros.conf` (`sap_logserv_idx_macro`, `sap_logserv_audit_idx_macro`, `sap_logserv_cloud_provider_default_macro`; the allow-list consistency suite compares the two), exactly: the bare name for a stanza without arguments, or `name(a, ...)` with as many arguments as a `name(n)` stanza declares. Whitespace around the name, a case variant, or `name()` on a stanza without arguments is refused. A macro's definition is not visible to the guard, and the Splunk MCP Server's own parser check runs with macros unexpanded, so any other macro could hide any command.

Why each command is listed: `collect` and its aliases `stash`, `summaryindex` and `sumindex`, `mcollect` and `meventcollect` write to an index; `outputlookup` and `outputcsv` write lookup files, and `outputtext` rewrites each result's `_raw` into `_xml`; `delete` deletes events; `sendalert` and `sendemail` trigger alert actions; `script`, its alias `run`, and `runshellscript` run scripts; `dump` writes search results to files on the search head; `tscollect` writes tsidx summaries; `createrss` adds an item to an RSS feed on the search head (the search app's `commands.conf` marks it `is_risky`); `rest` reads any REST endpoint the user may read, including `storage/passwords`, whose `clear_password` is every stored credential, decrypted; `outputtelemetry` sends rows to Splunk's telemetry service; the third-party `curl` and `wget` (for example from TA-webtools) send HTTP requests to any URL, and `sendresults` emails results; `ai` (Machine Learning Toolkit / AI Toolkit) sends the piped rows to the LLM configured there, which would break the App's rule that no event data reaches an AI vendor; `deletemodel` deletes a saved model; `savedsearch`, its aliases `macro` and `savedsplunk`, and `map` run another saved search (or a search per result row), which would reach the rollup, retention and backfill searches the saved-search allow-list keeps out.

Detection (the command, word and external-lookup regexes are all case-insensitive):

- The command regex, `(?:^|\||\[)\s*(<command>)\b`, runs on the quote-blanked copy. It fires at the start of the query, after a pipe, or after a subsearch bracket, so `| collect index=x`, `[| outputlookup x]` and a query that starts `outputlookup x` are all caught, while a field value such as `action="collect_data"`, a field named `fitness` or `rest_time`, or a bracketed tag inside a quoted string (`search "[DELETE]"`) is not.
- The word regex, `\b(<word>)\b`, runs on the raw query and then on `dequoted`, and fires anywhere, which catches `| from savedsearch:X`, `| union savedsearch:X`, `[savedsearch X]`, `| from "savedsearch:X"` and `| "saved"search X`. A field such as `savedsearch_name` is not affected, because of the word boundary. The external-lookup regex works the same way (`dnslookup_cache` passes).

Known, deliberately conservative false positives: the words `savedsearch`, `savedsplunk` and `dnslookup` inside quoted text (for example `index=_audit "savedsearch"`), and words that only form once quote characters are removed (`"saved""search"`, `x="dns"lookup`); a backtick, or three, inside a quoted value; a query that starts with a command word, plain or quoted (`delete ...`, `"run" ...`, `'run' ...`), which Splunk would read as a search term; a `|` or `[` inside a single-quoted string, read as a command position; a `fit` followed anywhere later by the word `into`, even when `into` belongs to another command or to quoted text (`| fit X | stats count by into`, `| fit X by "a into b"`, `| fit X | eval note="into"`, or `into` in a later subsearch); and a backslash-escaped double quote outside a quoted string. Read-only queries with apostrophes (`"don't"`) and single-quoted field names that spell nothing forbidden pass the denylist. A denylist refusal names no other command or macro; with the allow-list behind it there is no perimeter left to map, so allow-list refusals name the refused command or lookup and the primers list the allowed commands exactly. A macro that takes arguments needs a review before it is added to `macros.conf`: its arguments are substituted into its definition, so one that puts an argument where a command can go would let the arguments carry any command.

### The allow-list (`analyzeAdHocSpl`)

`analyzeAdHocSpl(query): AdHocSplAnalysis` runs the denylist first (a denylist refusal keeps its operator, and `command` is set when the operator is a forbidden command or word), then:

1. **Data scope** on the raw query, double-quoted text blanked (`index_not_allowed`): an `index=`, `index!=`, `index==`, `index::` or `index IN (` term (`INDEX_TERM_RE`, also a double-quoted `"index"` name); `OR` or `NOT` right before, or `OR` right after, `` `sap_logserv_idx_macro` `` (Splunk binds `OR` tighter than the implied `AND`). A backtick inside quoted text is `macro_position`.
2. **The lexer** (`lexSpl`): its problems become `ambiguous_single_quote`, `unbalanced_bracket`, `escaped_outside_quotes` (a backslash outside double quotes) and `macro_position` (a macro written against other text, the lexer's `macro_adjacent`); `too_deep` is reported as `subsearch_not_allowed`.
3. **The command tree**, every pipeline (`checkPipeline`, with the mode `main`, `filter` for a `search` subsearch, `arm` for `append` / `appendcols` / `join`, `pipe` for `appendpipe`): every command name in `ALLOWED_SPL_COMMANDS` (47 commands, each one the Tier 2 reader reads in full; `command_not_allowed`, also for a command with no name; `union` is off the list - Splunk's search parser reports every union rewritten, as `search … | append [...]` or `multisearch`, so `checkParserAgreement` would refuse each one - and its refusal carries `COMMAND_INSTEAD.union`, which tells the model to combine searches with `append`); every macro where it cannot change the scope — the data macro as the first term of a search or right after `WHERE` in `tstats`, the audit macro never (`index_not_allowed`), an App macro that expands to a command only as that whole command (`macro_position`); the start of the query and of every subsearch arm (`query_start`): the data macro as the first term of its search, `| inputlookup`, `| tstats … WHERE <data macro>` or `| makeresults`, and every later `tstats` too; `lookup` / `inputlookup` names in `ALLOWED_SPL_LOOKUPS` (the App's `transforms.conf` lookup stanzas minus `EXCLUDED_SPL_LOOKUPS`: the two Data Doctor collections and the two ES feeds; `lookup_not_allowed`) and no eval `lookup(`, whitespace or a line break before the parenthesis included (`eval_lookup`); subsearch groups only in `SUBSEARCH_HOSTS`, one for `appendpipe` (`subsearch_not_allowed`); a filter subsearch ending with `fields` / `table` naming its fields, none `search` or `query` (`subsearch_fields`).

A refusal carries `command`: the refused name, through `safeName` (`[A-Za-z0-9_.:-]{1,64}`, else `(unnamed)`). A pass carries `commands` (the top-level command names, macro commands expanded) and `startsWithDataMacro`.

**The search-parser check** (`checkParserAgreement(local, body)`, called by `vetAdHocQuery`): the reply of `search/parser` (parse only, macros expanded, in the user's namespace of this App) must have a `commands` list (`readParserReply`; a reply without one, or one with more than `PARSER_REPLY_MAX_NODES` nodes, is `parser_unavailable`); every `command` anywhere in it must be allowed (in the parser's replies only the top-level commands are command nodes: a subsearch is text, macros expanded, inside the raw arguments of the command that holds it); its top-level list must equal `commands` (`PARSER_COMMAND_ALIASES`: `bucket` = `bin`); when the query starts with the data macro, the first search's raw arguments must start with the shipped definition, not followed by `OR` / `NOT` (`dataMacroAsShipped`; raw arguments that still hold a backtick are not judged); no top-level command's raw arguments may name another index (`foreignIndexTerm`); and every top-level `lookup` / `inputlookup` must name, in its raw arguments, one of `ALLOWED_SPL_LOOKUPS` (`parserLookupName`: the first word after the options `PARSER_LOOKUP_OPTIONS` documents for that command, each with a plain value; the word must end at whitespace or the end of the text; anything it cannot read - no raw arguments, an option the command does not document or one in another case, a quoted or glued option value or name - refuses too, with `command` = the command). The raw arguments are the command's text after its name, macros expanded, as the parser returns them (for example `logserv_wp_perf_rollup where metric="wperr" `); a lookup or command inside a subsearch is no command of its own in the reply, so the lexer alone checks it, and one that a shadowed macro brings into a subsearch is caught by neither check (only an index term it brings in is, through `foreignIndexTerm` on the raw arguments of the command that holds the subsearch). Any disagreement is `parser_mismatch`. For a query that starts with the data macro this also catches a macro of the same name that the user's context shadows; the macro after `WHERE` in `tstats` or at the start of a subsearch is checked only through `foreignIndexTerm`. A `parser_mismatch` reason quotes at most one command name from the reply, through `safeName`; no other reply text reaches the vendor.

**Limits.** Catalog searches are not checked this way: a `local/macros.conf` override in this App, the user's private macro or another app's globally exported macro of the same name can still change what a catalog search reads; keeping the three macros unshadowed is the admin's responsibility (`splunk btool macros list <name> --debug` shows the one in effect). The parser check depends on `search/parser` being reachable; when it is not, every free-form query is refused.

**Audit on block:** (none when the user stopped the turn while the parser call ran: `parser_unavailable` with the turn's signal aborted, `stoppedByUser` in the hook) `security_blocked_spl` event with `spl` (the query, truncated to 1000 chars) + `operator` (the matched command or word, or `inline_comment` / `unbalanced_backtick` / `unterminated_quote` / `escaped_quote` / `external_lookup` / `fit_into` / `macro`; `macro` is reported both for a macro outside the App's own and for the `macro` command, and `command` tells them apart — the macro's name as written (`foreignMacroName`), or `macro`; for the allow-list `command_not_allowed`, `query_start`, `index_not_allowed`, `lookup_not_allowed`, `eval_lookup`, `subsearch_not_allowed`, `subsearch_fields`, `macro_position`, `ambiguous_single_quote`, `unbalanced_bracket`; for the parser check `parser_mismatch`, `parser_rejected` or `parser_unavailable`) + `command` when the refusal is about a command, lookup or macro. The Session-audit modal and the Audit Log viewer show it next to the operator. The AI receives `Tool call refused by the App before it ran: ` followed by the guard's reason (see **Failed calls and refusals** above), and can recover by writing a different query.

**Scope:** only AI-authored `splunk_run_query` SPL. Pre-authored saved searches dispatched via `splunk_run_saved_search` are NOT subject to the guard — their SPL is reviewed at build time, and only the intent map's names can be dispatched (see **How a saved-search call is dispatched** above).

### Splunk reserved-field gotcha

The `category` field on these events is a Splunk reserved name: Splunk's automatic event classification fills it (with `unknown` for this sourcetype), and `spath` does NOT overwrite it. The viewer's SPL therefore runs `| eval category=json_extract(_raw, "category")` after `spath`. It re-derives `user` the same way, `| eval user=json_extract(_raw, "user")`: when the base search filters on `user`, Splunk extracts the field to apply the filter and `spath` adds the same value again, so without the `eval` the field has two values and a name shows twice. Replicate both in custom queries.

## :material-circle-box:{ .taiconcolor } Adding a New Predefined Prompt

The catalog is compiled into the App: the intent map is imported into the bundle, and its saved searches ship in `default/savedsearches.conf`. A new or changed prompt therefore needs a rebuild of the App from source ([Building the Packages from Source](build-from-source.md)) and a redeploy; on Splunk Cloud the rebuilt App goes through private-app vetting again. The steps:

1. Edit `default/data/mcp/logserv_intent_map.json` — add a new entry to the `prompts` array. Required fields: `id`, `pack` (`sap_basis` | `security` | `operations` — drives which prompt-browser tab the prompt appears under), `savedSearch`, `label`, `description`, `spl`, `renderHint`. Type-optional but present on every shipped prompt (omitting them silently degrades the guidance card, the deep-dive links, and the Dashboard-Focused tab): `interpretation`, `nextSteps`, `dashboard`. Truly optional: `chartHint`, `chartPalette`.
2. Edit `default/savedsearches.conf` — add a stanza with the same name as the prompt's `savedSearch` field. The SPL must match byte-for-byte.
3. Bump the intent map's top-level `version` field.
4. Run `yarn check:intent-map` — it also runs automatically as the FIRST step of `yarn build` / `yarn build:templates-only`, so drift fails in seconds, before webpack. It asserts byte-equality between each prompt's `spl` and its `savedsearches.conf` stanza, and that every prompt-shaped stanza has a prompt (scheduled rollup jobs are exempt). The sibling gate `yarn check:diagnostics` runs the other consistency-test suites plus live conf-drift checks and must also pass for any build.
5. **Pre-deploy SPL dry run.** Run the new prompt's SPL in Splunk Web's Search app against live data (for example over the last 30 days) and confirm the result has rows with the expected fields. Field-extraction problems often show only against live data.
6. Bump UI App `[install] build` in `app.conf` to bust Splunk Web's static-asset cache, then build and deploy the App.

### Intent map JSON schema

```typescript
interface IntentMapPrompt {
    id: string;
    pack: 'sap_basis' | 'security' | 'operations';
    savedSearch: string;
    label: string;
    description: string;
    spl: string;
    renderHint: 'table' | 'timechart' | 'kpi' | 'pie';
    chartHint?: 'timechart' | 'kpi' | 'pie';
    chartPalette?: 'volume' | 'errors' | 'errors-2' | 'errors-3' | 'auth' | 'status' | 'categorical' | 'neutral';
    dashboard?: string | string[];
    interpretation?: string;
    nextSteps?: Array<string | { text: string; savedSearch?: string; spl?: string }>;
}
```

### Splunk risky-command safeguard

Splunk Web's Search app asks for confirmation before it runs a search that arrives in a link (a URL to `/app/search/search?q=...`, which is what the **↗ Run SPL** chips open) and contains a command Splunk marks as risky. Splunk's SPL-safeguards documentation for 9.4 lists `collect`, `delete`, `dump`, `map`, `mcollect`, `meventcollect`, `outputcsv`, `outputlookup`, `run`, `runshellscript`, `script`, `sendalert`, `sendemail` and `tscollect`. An app can mark further commands with `is_risky = true` in its `commands.conf`; the comments in `utils/splGuard.ts` record that the search app does this for `createrss`. The list can differ in another Splunk version and grow with the apps installed, so check it on the version you ship to.

Scan all SPL — including `nextSteps.spl` deep-dive strings — for these commands before shipping. Every command named above is also in `FORBIDDEN_SPL_COMMANDS` in `utils/splGuard.ts`, so a scan against that list covers them. Rewrite `map`-style cross-row dispatches to first-class subsearch syntax: `[ search ... | top 1 X | fields X ]`.

## :material-circle-box:{ .taiconcolor } System Primer Architecture

Two primer variants ship: `SYSTEM_PRIMER_TIER1` and `SYSTEM_PRIMER_TIER2`. Both live in `hooks/useAIAssistant.ts` as module-private constants (only `SAVED_SEARCH_DASHBOARDS` and the hook itself are exported — a consumer needing primer text must export it first). They share most of their content; the differences:

- **Tier 1** primer instructs the AI that summaries it receives are count + execution-time only, and to write SHAPE-aware narrative ("X rows returned for the search's rolling window") rather than inventing concrete values.
- **Tier 2** primer informs the AI that summaries include aggregated metadata (per-column cardinality, top-N values + counts, numeric stats, time range), and instructs it to ground every claim in the actual values from the aggregates. Its TIER 2 SUMMARY SHAPES block explains `col_N` and the withheld-names line, `<redacted-…>` tags, `values withheld`, `not in row form` and `Time range: not shown`, and tells the model never to guess, recover or attribute a withheld name or a redacted value and to name an identifier only when it appears in clear; synthesis rule 3 grounds claims in values shown in clear.

Both primers include:

- The TOOL_RESULT_DATA boundary block (`<TOOL_RESULT_DATA>...</TOOL_RESULT_DATA>` sentinels)
- The TIME-WINDOW REASONING block
- The canonical saved-search catalog
- The LogServ data model (sourcetypes + key fields, for ad-hoc SPL)
- The decision rule for `splunk_run_saved_search` vs `splunk_run_query`
- The SYNTHESIS RULES section: lettered finding format, severity-dot rendering, citation format, etc.

**Power Mode augmentation:** when the user has Power Mode on, `POWER_MODE_RULE_SUFFIX` is appended to the primer at dispatch time via `unwrapVisible(content) + suffix` then `markVisible()` (the brand type can't widen back automatically).

## :material-circle-box:{ .taiconcolor } Pre-Resolving Drill-Down URLs at the Orchestrator Layer

The drill-down chip URLs (`↗ Dashboard`, `↗ Run SPL`) are pre-resolved at the AIAssistant.tsx layer, where each tool result's exact dispatch window is known. The resolved URLs are stored on the `citationLookup` Map for the chat parser to consume:

```typescript
const citationLookup: Map<string, { toolUseId: string; splUrl?: string }> = new Map();
toolResultsInOrder.forEach((tr) => {
    if (tr.displayName) {
        const splUrl = tr.spl
            ? buildSplunkSearchUrl(tr.spl, tr.earliest, tr.latest)
            : undefined;
        citationLookup.set(tr.displayName, { toolUseId: tr.toolUseId, splUrl });
    }
});
```

The chat-side renderer (`ChatMessage.tsx`) is dumb — it just renders `<a href={entry.splUrl}>` when the lookup carries a URL. This avoids duplicating SPL-lookup logic at every consumer.

Same pattern applies to the dashboard chips: the `dashboardLinks` are resolved once via `resolveDashboardLinks(slugs)` at the orchestrator and consumed as `{slug, name, url}` triples.

## :material-circle-box:{ .taiconcolor } Legal Acknowledgement Modal Trigger Logic

Two legal acknowledgement modals gate Settings save flows:

- **Enable Acceptance Modal** — gates `enabled = true` saves.
- **Forwarder Disabled Acceptance Modal** — gates `audit_forwarder_enabled = false` saves.

Both follow Splunk's `splunk_instrumentation` `optInVersion` framework with one extension. The trigger logic is:

```typescript
isEnableTcPending = (
    (saved.enabled === false && draft.enabled === true)  // deliberate toggle-on
    OR
    (currentOptInVersion > acknowledgedVersion)          // version bumped
)
```

The pure `optInVersion`-only path is what Splunk's stock telemetry uses (acknowledge once per version, durable until bump). We added the deliberate-toggle-transition trigger because re-enabling AI Assistant after a disable is a deliberate user action that warrants re-acknowledgement of the legal posture each time. The acknowledged version is stored once per deployment (KV Store collection `logserv_ai_assistant_acks`, `_key` = the stanza name), not per user, and a Yes and a No both record it.

- **A No on the enable re-ask** (the AI Assistant already on) turns the AI Assistant off: it first writes `enabled = false` - the rest of the draft is not applied - and then records the No, so a failed write leaves the question pending. The turn-off writes the page's settings whole, like every Save: a partial write would merge onto `readAIConfig()`, which falls back to the conf or the defaults when the KV read fails. The page stays busy until the No is recorded, and the No's audit event records the saved provider.
- **Closing.** The dialog closes before the page state changes, and an answer that cannot be recorded also closes the dialog, so its error is seen. The forwarder dialog likewise closes before a record or save error is shown.
- **Audit events.** `handleForwarderChoice` posts the forwarder acknowledgement's audit event as soon as the answer is recorded, before the save a Yes goes on to. `AuditWriter.postOneOff` reads the local index and the forwarder settings before its first await, so the settings in place when a one-off event is posted decide where it goes, and a failed forward's record goes to the event's index.
- **Provider names.** On a re-ask the enablement dialog names `saved.provider`; when the same save changes the provider, the dialog also gets `pendingProviderName`.

`telemetryConfApi.ts` exposes `readTcAcknowledgement(stanza)` / `writeTcAcknowledgement(stanza, choice, version)` parameterized by stanza name. The two modal stanzas are constants: `STANZA_FORWARDER_TC` and `STANZA_ENABLE_TC`.

The legacy conf-writer path coerces `yes`/`no` to `'1'`/`'0'`; the KV Store path stores the strings as-is. The audit event preserves the literal string in `_raw`, so the audit event is the canonical record while the stored acknowledgement is the state marker.

## :material-circle-box:{ .taiconcolor } Why Primer Rules Beat Other Fixes (TIME-WINDOW REASONING)

One alternative fix was considered before settling on primer rules for the time-window reasoning behavior: **surfacing the dispatch window in Tier 2 metadata even for non-`_time` results**, which would let the AI see the window directly without reasoning about it. Higher engineering effort than primer rules; deferred unless rules alone don't move the needle.

Primer rules were the cheapest test of "is this a primer-rules issue?" and it worked: same prompt, same data, dramatically better self-correction behavior in one turn instead of needing a follow-up prompt to re-rank cumulative-noise findings.

This is the canonical pattern: when the AI has the data but isn't using it correctly, primer rules are the cheapest first attempt. When the AI doesn't have the data, metadata expansion is the next step.

## :material-circle-box:{ .taiconcolor } Splunk Static-Asset Cache Busting

Splunk Web caches the React bundle's asset URL under a hash that includes the `[install] build` integer in `app.conf` (`src/main/resources/splunk/default/app.conf`). **Re-deploying the same build number with new bytes serves stale assets even after Splunkd restart.** Always bump the build number for any meaningful code change. webpack also reads the version and build from that file at compile time for the About dialog.

The 3-part SemVer in `[id] version` (and `[launcher] version`) is independent of the build number and changes only on user-facing version bumps. AppInspect requires a 3-part SemVer version there.

## :material-circle-box:{ .taiconcolor } Live UI Refresh on Settings Save

When the admin saves a config change in the General tab that affects what users see (master `enabled` toggle, `mcp_required`, `power_user_roles`, etc.), the React app re-runs `loadAIAssistantConfig()` immediately and re-applies the new config to the running session. No page reload required.

Implementation: `App.tsx` passes a callback (`refreshAIConfig`) that re-reads the config with `loadAIAssistantConfig()`, which goes through `readAIConfig()`: the KV Store collection `logserv_ai_assistant_settings` first, then the conf, then the defaults (`writeAIConfig` clears the read cache, so the read sees the new values). The callback is threaded `App → AppShell (onAIConfigSaved) → AIAssistantSettings (onConfigSaved) → GeneralPanel`, called after `writeAIConfig` succeeds. Affected props are recomputed on the next React render and the dependent UI re-renders accordingly (e.g., the **AI Assistant** button in the header appears / disappears).
