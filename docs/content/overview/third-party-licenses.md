# Third-Party Software Licenses

Splunk for SAP LogServ bundles third-party software. The LogServ App, a webpack-built React single-page application, bundles open-source npm packages and three font families, and it includes search-time parsing content taken from two archived Splunk add-ons. The Data TA and the Azure and GCP ingest add-ons bundle nine open-source Python packages, and their configuration pages, generated by Splunk's UCC framework, carry UCC's prebuilt React bundle. Each component carries its own license, and per those licenses we preserve attribution and ship the full license text with each package.

## Where to find the full notices

The list of third-party npm packages in the App's build tree — names, versions, declared licenses, and full license text — is delivered in two places:

- **Inside the App tarball** — `splunk_app_sap_logserv/THIRD-PARTY-NOTICES.md` (the file is at the root of the installed app directory after extraction)
- **At the source-tree root** — the same file lives at the root of the GitHub release source tarball

Each add-on ships its own `THIRD-PARTY-NOTICES.md` for its Python packages; see [Python packages in the add-ons](#python-packages-in-the-add-ons).

The App's file is generated at build time from the build workspace's resolved `node_modules/` tree. It lists every package at the top level of that tree, at the version installed there: the libraries bundled into the App's JavaScript, and also the build, lint, type-check and test tools used to produce it (webpack, TypeScript, Babel, ESLint, Stylelint, Prettier, Jest and their dependencies), which are not shipped. The list is a deliberate superset for attribution. About 300 of the packages are reachable from the App's runtime dependencies, and webpack bundles only the code the App imports.

A copy of a package that the tree holds nested inside another package, at a different version, is not listed separately. In the v0.1.2 build tree, 32 such copies are reachable from the App's runtime dependencies, for example `d3-scale` 4.0.2 under `@splunk/visualization-canvas`, beside the listed `d3-scale` 3.3.0. Each of them is under the MIT, ISC or BSD-3-Clause license, but not always under the license of the version that is listed: several `d3-*` packages are BSD-3-Clause in the listed version and ISC in the nested one, or the other way round.

The file's sections on the absorbed Splunk add-ons and the bundled fonts are fixed text that the build writes each time.

### Notes

- **No GPL/AGPL/LGPL components** are included in the App's npm dependency tree. The npm license posture is fully compatible with commercial redistribution under the standard Splunkbase model.
- **One file-level weak-copyleft component is bundled: `elkjs`** (EPL-2.0, the Environment Topology layout engine), unmodified. EPL-2.0 is file-scoped copyleft (not project-scoped like GPL), and its obligations are satisfied by preserving the license text and not modifying the source, which we do. It is not in the GPL/AGPL/LGPL family. (In the 0.1.x line, the elkjs entry joined the generated notices in App build 333, when the package's formal dependency declaration was added.) `axe-core` (MPL-2.0) is in the build tree only as a dependency of the `eslint-plugin-jsx-a11y` lint plugin and is not in the shipped JavaScript.
- **Two packages without a declared `license` field** — `@mapbox/jsonlint-lines-primitives@2.0.2` and `uuid-v4@0.1.0` — are present as transitive dependencies. Both are de-facto open-source and have been on the public npm registry for years; reviewers preparing legal attestations should consult the upstream repositories listed in the per-component entries of `THIRD-PARTY-NOTICES.md` for any final disposition.
- **`@splunk/*` packages** (27 in total). Eleven declare `SEE LICENSE IN LICENSE.md`: the `@splunk/visualization*` family, `@splunk/charting-bundle` and `@splunk/async-dynamic-options-evaluator`. They are covered as a Splunk Extension under §1.C of the Splunk General Terms, the standard mechanism for redistributing Splunk UI libraries inside a Splunkbase-distributed app. The other 16, such as `@splunk/react-ui`, `@splunk/themes` and `@splunk/splunk-utils`, declare Apache-2.0 and are counted in the Apache-2.0 row above.

### Scope

The sections above cover the LogServ App's npm dependencies, its bundled fonts and the absorbed Splunk add-on content. The add-ons' Python packages and the notices of their UCC configuration pages follow.

## Known advisories: urllib3 1.26.20

The Data TA and the Azure and GCP ingest add-ons bundle urllib3 1.26.20, which
vulnerability scanners report as affected by seven advisories: CVE-2025-50181, CVE-2025-66418, CVE-2025-66471,
CVE-2026-21441, CVE-2026-44431, CVE-2026-97687 and CVE-2026-97689. We analysed each against the add-ons' code, and none
affects them as shipped:

- **No add-on code uses urllib3.** It is loaded only by Splunk's solutions library (solnlib), whose REST client talks
  to the local splunkd management port (by default `127.0.0.1:8089`) with the add-on's own session key. The add-ons'
  outbound connections (Azure Storage and the Google Cloud APIs) use Python's standard library, and no script in the
  Data, Azure or GCP add-ons imports `requests` or `urllib3`, directly or through `splunk_aoblib`.
- **Three need code paths that are never taken** - urllib3's redirect handling with retries turned off, following
  redirects while streaming a response, and passing credentials on across redirects through a proxy:
  CVE-2025-50181, CVE-2026-21441 and CVE-2026-44431.
- **Three need a malicious server on the splunkd management port** - decompression and chunked-response attacks:
  CVE-2025-66418, CVE-2025-66471 and CVE-2026-97689. With the default `mgmtHostPort` that is the loopback interface,
  so an attacker would already need access to the host; if you bind the management port to a network address, the
  protection rests on that network.
- **One needs an HTTPS proxy in splunkd's environment** - CVE-2026-97687. If splunkd's environment sets `HTTPS_PROXY`,
  also set `NO_PROXY=127.0.0.1,localhost` (see [Installing the Data TA](../install-setup/install-ta.md)).

**Why the add-ons do not ship urllib3 2.x.** urllib3 2.x requires OpenSSL 1.1.1 or later, and the Python in Splunk
Enterprise 9.4.3 is built with OpenSSL 1.0.2 (`OpenSSL 1.0.2zl-fips` on our test systems), so urllib3 2.x cannot load
there. The releases that fix the newest advisories also require Python 3.10 or later, while Splunk 9.4 runs Python
3.9, and the current splunktaucclib release requires `urllib3<2`. Splunk Enterprise 9.4.3's own Python includes
urllib3 1.26.19. We expect to stop bundling urllib3, or to move to a 2.x release, when the add-ons' minimum supported
Splunk version moves past 9.4.

## Refresh policy

The App's `THIRD-PARTY-NOTICES.md` is regenerated from the resolved `node_modules/` tree at every release. v0.0.5.0 used a one-off generation pass; v0.0.6 and every later release (including v0.1.1 and v0.1.2) refresh the file as part of the standard `yarn build` pipeline (`bin/generate-third-party-notices.js`, run after the webpack output lands in `stage/`), so every package at the top level of the build tree, bundled or not, appears in the notices at the version installed there; nested copies at other versions are not listed separately (see [Where to find the full notices](#where-to-find-the-full-notices)). One package was missed this way in earlier builds: `elkjs`, the Environment Topology layout engine, has no entry in the notices of v0.0.6 builds 252–266, or of the v0.1.1 builds before 333 that bundle it, because it was not declared as a dependency ([Release Notes: 0.0.6](release-notes-0.0.6.md#third-party-software-attributions), [build 333](release-notes-0.1.1.md#elkjs-license-attribution-restored-in-the-shipped-notices-build-333)). The add-ons' notices files are maintained by hand, beside their pinned `lib/requirements.txt`.
