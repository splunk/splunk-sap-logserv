    Where Each Package Goes¶

    This page is the one place that says which Splunk instance gets which package, for every supported topology. Use it to plan your install; the install steps are on the pages it links to.

    Package Matrix¶

    SH = the search tier: the search head, the Splunk Cloud search head, or every member of a search head cluster (through the deployer). IDX = indexers. HFs = heavy forwarders. DS = Deployment Server. On a single instance, install every required package on that instance.

    The four LogServ packages are the 0.1.2 tarballs in the release_binaries/ folder of the GitHub repository: splunk_ta_sap_logserv-0.1.2.tar.gz, splunk_app_sap_logserv-0.1.2.tar.gz, splunk_ta_sap_logserv_azure-0.1.2.tar.gz and splunk_ta_sap_logserv_gcp-0.1.2.tar.gz, with their AppInspect reports and a README that lists each file’s md5 and size.

    Notes¶

    • The rule behind the table. The Data TA goes where the data is parsed: the heavy forwarders that run the ingest inputs, or the single instance. The Deployment Server holds it to distribute it. The indexes are created on the indexer tier: a heavy forwarder parses each event before forwarding it, so the indexers need only the two index definitions.
    • Deployment Server: optional. With one, install the Data TA on the Deployment Server only, never also directly on the heavy forwarders it manages: a push replaces the forwarder’s copy of the app, local/ included. Nothing reaches the forwarders on its own. They must be deployment clients, and the Data TA arrives after its Configuration page is saved on the Deployment Server, the forwarders are added to the server class, and Deploy to Forwarders is clicked; each forwarder restarts when it arrives. See Distribute the Data TA to Heavy Forwarders. A Splunk Cloud stack is never a Deployment Server: run your own, or install the Data TA directly on each heavy forwarder.
    • Ingest add-ons are installed directly on each instance that runs an input, never through a Deployment Server. Their credentials and inputs live in their own local/, which a push would replace. When a Deployment Server manages the Splunk Add-on for AWS on an instance, the AWS S3 Direct screen there only generates the configuration for an administrator to apply. Install the Azure or GCP add-on on each heavy forwarder that may run an input, but run one input for each queue or subscription: every input keeps its own record of what it has read, so a second input on the same queue can index a redelivered message twice. For Google Cloud, use the LogServ GCP add-on, not the general-purpose Splunk Add-on for Google Cloud Platform (Splunkbase 3088), which cannot decompress the gzipped LogServ objects. One heavy forwarder can run the add-ons of several clouds; see More Than One Cloud.
    • AWS inputs. The SQS-Based S3 inputs read the queue of your scenario (SAP’s queue for Connect, the queue in your Secondary account for Filter or Copy) and download each object from the bucket its notification names (SAP’s bucket for Connect and Filter, your copy bucket for Copy). The index = sap_logserv_logs setting that sends the events to the right index is on these inputs, not in the Data TA.
    • Search heads. We strongly recommend against the Data TA and the ingest add-ons on a search head, Splunk Cloud included: ingest belongs on the heavy forwarders. Nothing blocks it, and a search head that runs the inputs itself (the “Splunk Cloud only” row) needs the Data TA there; see Running the TAs on a search head. On the Splunk Cloud Victoria Experience, installing the Data TA and the LogServ App on the search head and opening the AWS S3 Direct screen there have been checked; creating and running inputs on a Splunk Cloud search head has not been tested by the project, and the LogServ Azure and GCP add-ons have not been installed on one. On the Classic Experience, inputs run on an Inputs Data Manager (IDM). The Data TA’s app.manifest does not list the forwarder workload (_forwarders); whether Splunk Cloud installs it on an IDM has not been tested, and neither has this path.
    • Search-tier add-ons go on the search tier only. For LogServ data, CIM (1621), Windows (742) and Unix/Linux (833) provide search-time content only: the Data TA parses every event as sap_logserv_logs and only then routes it to XmlWinEventLog, linux_secure and the other sourcetypes, so these add-ons’ parse-time settings never apply. No LogServ package extracts XmlWinEventLog fields, so without 742 the Windows dashboard’s Event Code, Severity and Service panels stay empty. The App parses its other Linux sourcetypes itself; 833 provides the CIM fields of linux_secure. If you use one of these add-ons’ own inputs for other data, follow that add-on’s placement guidance for them.
    • Enterprise Security. The App’s ES content does its work only where ES runs, so install the LogServ App and its search-tier add-ons on the search head that runs ES too. On Splunk Cloud, ES has its own search head, separate from the one your users open for other apps (Enterprise Security Integration: Prerequisites).
    • No standalone Squid Proxy or ISC BIND add-ons. Their parsing is built into the LogServ App. If either is installed beside it, both parse the same events, and the App’s home view shows a banner recommending you remove the standalone add-on.
    • Splunk Cloud indexes. Create both indexes yourself, in Settings > Indexes or with the Admin Config Service (ACS), with the retention you want, before any data arrives. Do this also when the Data TA is installed on the Cloud stack: Splunk does not document that a private app’s index definitions create the indexes there.
    • The AI Assistant ships disabled. It needs the Splunk MCP Server 1.1.0 or later on the same search head as the LogServ App: the predefined prompts use its Run Saved Search tool, which first shipped in 1.1.0. The App’s health check blocks only versions below 1.0.3 (the CVE-2026-20205 fix) and sets no upper bound; the newest version verified is 2.0.0. See Set Up the AI Assistant.
