    AWS Remote S3 Connect with an EC2 Instance Role¶

    Introduction¶

    Use this page when your heavy forwarders run on Amazon EC2 and you may not create IAM users or long-lived access keys. It sets up the same scenario as the AWS Remote S3 Connect Setup Guide, without the IAM user: the Splunk Add-on for AWS takes temporary credentials from the heavy forwarder’s EC2 instance profile, and no access key is created in AWS or stored in Splunk.

    As in the main guide, the SAP ECS account holds SAP’s S3 bucket and SQS queue, and the Secondary account is your own AWS account.

    Secondary account                              SAP ECS account
+---------------------------------------+      +----------------------------+
|  Heavy forwarder (EC2 instance)       |      |                            |
|    instance profile role              |      |  SQS queue and S3 bucket   |
|         |                             |      |                            |
|         | sts:AssumeRole              |      |  The queue access policy   |
|         v                             |      |  and the bucket policy     |
|  IAM role splunk-logserv-ta-role  ---------->|  name this IAM role        |
|    reads the queue and the bucket     |      |                            |
+---------------------------------------+      +----------------------------+

    This page uses two IAM roles, and names them the same way throughout:

    Name on this page What it is
    Instance profile role The IAM role in the instance profile attached to each heavy forwarder EC2 instance. It needs only sts:AssumeRole on the role below
    splunk-logserv-ta-role The IAM role in your Secondary account that holds the permissions on SAP’s SQS queue and S3 bucket. SAP names its ARN in the SQS queue access policy and the S3 bucket policy

    This page does not apply when the input runs on a Splunk Cloud instance, on a host outside EC2, or on an EC2 instance that cannot have an instance profile: use the IAM user in the main guide there. The Filter and Copy scenarios still need the IAM user.


    Before You Begin¶

    • Splunk Add-on for AWS 8.2.2 or later, installed directly on each heavy forwarder (Install the Splunk Add-on for AWS).
    • Check These First in the main guide applies here too: the prerequisites, the Data TA, cloud attribution, filtering and the first start.
    • IAM permissions for you: create and edit IAM roles and policies in the Secondary account; for scenario A also create a CloudFormation stack; and if a heavy forwarder has no instance profile yet, iam:CreateInstanceProfile, iam:AddRoleToInstanceProfile, iam:PassRole and ec2:AssociateIamInstanceProfile.
    • Each heavy forwarder can reach the instance metadata service (169.254.169.254) as the Splunk user. Heavy Forwarder Requirements has the full list and a check.


    Find Your Scenario¶

    Look in the IAM console and the CloudFormation console of your Secondary account, and pick the first row that matches. The scenario decides only step 3; every other step is the same for all three.

    What your Secondary account has today Your scenario
    The CloudFormation stack from the standard Remote S3 Connect template (splunk-logserv-remote-s3-connect.yaml). It created the IAM user splunk_logserv_user and the IAM role splunk-logserv-ta-role, and your inputs use that user’s access key Scenario B: switch the deployed stack’s IAM role to the instance profile
    An IAM role you want to reuse or must create yourself, without CloudFormation: a splunk-logserv-ta-role made by hand or by your own tooling, a role with another name, or a customer managed policy you want to attach Scenario C: create or reuse the IAM role and policy by hand
    Nothing for LogServ yet: no IAM role named splunk-logserv-ta-role and no Remote S3 Connect stack Scenario A: deploy the instance-role CloudFormation template

    If the account has a Remote S3 Filter or Remote S3 Copy stack, this page does not apply. Never update one of those stacks with the template on this page.

    Step Scenario A Scenario B Scenario C Where

    3. Set up splunk-logserv-ta-role Deploy the stack Edit the trust policy Create or reuse by hand AWS, Secondary account

    Configure each heavy forwarder directly, not through a Deployment Server. Several heavy forwarders can read the same SQS queue (Add Heavy Forwarders on the Same Queue): attach the same instance profile to each.


    1. Get SAP’s ARNs¶

    1.a Obtain the ARN of the S3 bucket, the ARN of the SQS queue and their AWS Region, as in 1. Obtain ARNs from SAP ECS Account in the main guide.

    1.b In your Secondary account, check under Account > AWS Regions that this Region is enabled.

    1.c Ask SAP whether the bucket or the queue is encrypted with a customer managed KMS key. If so, see Customer Managed KMS Keys before step 3.


    2. Find or Create the Instance Profile Role¶

    An EC2 instance has one instance profile, and an instance profile holds one IAM role. Do the part that matches each heavy forwarder.

    The instance profile role and splunk-logserv-ta-role are two different IAM roles. Do not attach splunk-logserv-ta-role (or the role whose ARN you give SAP in step 4) to the heavy forwarder instance: the input would then ask that role to assume itself, and AWS refuses that with AccessDenied. If the role you find or create in this step is the one that holds the queue and bucket permissions, see Troubleshooting.

    The Heavy Forwarder Already Has an Instance Profile¶

    Reuse it. Nothing on it changes except one inline policy in step 3.

    2.a In the EC2 console, select the heavy forwarder instance. On the Security tab, click the link under IAM Role. It opens the role in the IAM console.

    2.b Copy the role’s ARN and its name. The ARN looks like arn:aws:iam::<secondary-account-id>:role/<instance-profile-role-name>.

    AWS CLI 
    # The instance profile attached to the instance
aws ec2 describe-instances --instance-ids <instance-id> \
  --query 'Reservations[].Instances[].IamInstanceProfile.Arn' --output text

# The IAM role inside that instance profile
aws iam get-instance-profile --instance-profile-name <instance-profile-name> \
  --query 'InstanceProfile.Roles[].[RoleName,Arn]' --output text

    The Heavy Forwarder Has No Instance Profile¶

    2.c In the IAM console, click Roles, then Create role. Choose AWS service as the trusted entity type and EC2 as the use case. Add no permissions policies. Name the role, for example splunk-logserv-hf-instance-role, and create it. The console creates an instance profile with the same name.

    2.d In the EC2 console, select the heavy forwarder instance, then Actions > Security > Modify IAM role, choose the new role and click Update IAM role. Repeat for each heavy forwarder, and add the instance profile to the launch template of any heavy forwarder you build later. Splunk should not need a restart.

    2.e Copy the role’s ARN and name from its page in the IAM console.

    AWS CLI

    Save this as ec2-trust-policy.json:

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "ec2.amazonaws.com" },
      "Action": "sts:AssumeRole"
    }
  ]
}

    aws iam create-role --role-name splunk-logserv-hf-instance-role \
  --assume-role-policy-document file://ec2-trust-policy.json
aws iam create-instance-profile --instance-profile-name splunk-logserv-hf-instance-role
aws iam add-role-to-instance-profile --instance-profile-name splunk-logserv-hf-instance-role \
  --role-name splunk-logserv-hf-instance-role
aws ec2 associate-iam-instance-profile --instance-id <instance-id> \
  --iam-instance-profile Name=splunk-logserv-hf-instance-role


    3. Set Up the IAM Role splunk-logserv-ta-role¶

    Follow the one scenario you picked in Find Your Scenario, then go on to step 4.


    Scenario A: Deploy the Instance-Role CloudFormation Template¶

    The CloudFormation template splunk-logserv-remote-s3-connect-instance-role.yaml creates the IAM role splunk-logserv-ta-role with its trust policy and its inline policy, and adds the sts:AssumeRole inline policy to your instance profile role. It creates no IAM user and no access key.

    What does the CloudFormation template do?

    Creates the following resources in your Secondary account:

    • An IAM Role named splunk-logserv-ta-role
    • A trust policy on that IAM Role that lets one principal assume it: the instance profile role you enter in HeavyForwarderInstanceRoleArn
    • An Inline IAM Policy named splunk-logserv-ta-policy on that IAM Role. It allows reading and deleting messages on SAP’s SQS queue (sqs:ReceiveMessage, sqs:DeleteMessage, sqs:ChangeMessageVisibility, sqs:GetQueueAttributes), reading objects in SAP’s S3 bucket (s3:GetObject, s3:GetObjectVersion) and listing that bucket (s3:ListBucket)
    • Only if you fill in SapKmsKeyArns: a kms:Decrypt statement in that policy, on the KMS keys you list

    Updates one resource that already exists:

    • Only if you fill in HeavyForwarderInstanceRoleName: it adds an Inline IAM Policy named splunk-logserv-sqs-based-input-assume-role-policy to your instance profile role. It allows sts:AssumeRole on splunk-logserv-ta-role and nothing else. The role’s other policies and its trust policy are not changed

    Returns three stack outputs: SplunkLogServRoleArn (the ARN for steps 4 and 6), InstanceRoleGrant (whether the stack added the policy to your instance profile role) and YourAccountId.

    It creates no IAM User, no access key, no instance profile, no S3 Bucket and no SQS Queue, and it changes nothing in the SAP ECS account. Deleting the stack deletes the IAM Role and removes the inline policy from your instance profile role.

    A.1 In the CloudFormation console of your Secondary account, in the Region of SAP’s queue, click Create stack, then With new resources (standard). Upload the template file and click Next.

    A.2 Name the stack, for example splunk-logserv-remote-s3-connect-instance-role, and enter the parameters:

    Parameter Value
    CrossAccountSQSQueueArn The complete ARN of SAP’s SQS queue
    CrossAccountS3Bucket The name (not the ARN) of SAP’s S3 bucket
    SapKmsKeyArns Blank, unless SAP uses customer managed KMS keys. Then their ARNs, separated by commas with no spaces
    HeavyForwarderInstanceRoleArn The ARN of the instance profile role from step 2
    HeavyForwarderInstanceRoleName The name of that same role, without any path. Leave it blank only if that role is in another AWS account, then do C.3 in that account

    A.3 Click Next, check I acknowledge that AWS CloudFormation might create IAM resources with custom names, click Next, then Submit. Wait for CREATE_COMPLETE.

    A.4 On the stack’s Outputs tab, copy SplunkLogServRoleArn. It is the ARN for steps 4 and 6.

    A.5 Turn on termination protection (Stack actions > Edit termination protection). Deleting the stack deletes the IAM role, and SAP’s policies stop matching it (Do Not Delete and Recreate the IAM Roles).

    AWS CLI 
    aws cloudformation deploy \
  --region <region-of-the-sap-queue> \
  --stack-name splunk-logserv-remote-s3-connect-instance-role \
  --template-file splunk-logserv-remote-s3-connect-instance-role.yaml \
  --capabilities CAPABILITY_NAMED_IAM \
  --parameter-overrides \
    CrossAccountSQSQueueArn=arn:aws:sqs:<region>:<sap-ecs-account-id>:<queue-name> \
    CrossAccountS3Bucket=<bucket-name> \
    HeavyForwarderInstanceRoleArn=arn:aws:iam::<secondary-account-id>:role/<instance-profile-role-name> \
    HeavyForwarderInstanceRoleName=<instance-profile-role-name>

aws cloudformation describe-stacks --region <region-of-the-sap-queue> \
  --stack-name splunk-logserv-remote-s3-connect-instance-role \
  --query 'Stacks[0].Outputs' --output table

aws cloudformation update-termination-protection --enable-termination-protection \
  --region <region-of-the-sap-queue> \
  --stack-name splunk-logserv-remote-s3-connect-instance-role

    Continue with step 4.


    Scenario B: Switch the Deployed Stack’s IAM Role to the Instance Profile¶

    Your stack already created splunk-logserv-ta-role, and SAP’s SQS queue access policy and S3 bucket policy already name it. You add the instance profile role to that IAM role’s trust policy, switch the inputs, then retire the IAM user’s access key. The IAM role keeps its ARN, so SAP changes nothing, and the inputs keep working on the access key until you switch them.

    Leave the CloudFormation stack in place. Do not delete it: deleting it deletes the IAM role. Do not update it with a template that changes the IAM role either: CloudFormation would overwrite the trust policy you edit here. CloudFormation drift detection will report the trust policy you edit as modified, which is expected.

    B.1 In the IAM console, click Roles, open splunk-logserv-ta-role, click the Trust relationships tab, then Edit trust policy.

    B.2 Add the ARN of the instance profile role from step 2 to the Principal, next to the IAM user that is already there, and click Update policy:

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": [
          "arn:aws:iam::<secondary-account-id>:user/splunk_logserv_user",
          "arn:aws:iam::<secondary-account-id>:role/<instance-profile-role-name>"
        ]
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
    AWS CLI 
    # Show the trust policy in place, and save the edited document as trust-policy.json
aws iam get-role --role-name splunk-logserv-ta-role \
  --query 'Role.AssumeRolePolicyDocument' --output json

aws iam update-assume-role-policy --role-name splunk-logserv-ta-role \
  --policy-document file://trust-policy.json

    B.3 Do C.3: the inline policy that lets the instance profile role assume splunk-logserv-ta-role.

    B.4 Skip step 4, and do steps 5, 7, 8 and 9. In step 8 you switch your existing inputs, you do not create new ones.

    B.5 After step 9 shows data arriving through the instance profile on every heavy forwarder, retire the access key:

    • In the Splunk Add-on for AWS on each heavy forwarder, under Configuration > Account, delete the account that holds the IAM user’s access key.
    • In the IAM console, open the user splunk_logserv_user, click the Security credentials tab, and under Access keys choose Actions > Deactivate, then Delete.
    • Edit the trust policy of splunk-logserv-ta-role again and remove the IAM user’s ARN, so that only the instance profile role remains.
    • Leave the IAM user itself in place, without a key. The stack owns it.
    AWS CLI 
    aws iam list-access-keys --user-name splunk_logserv_user
aws iam update-access-key --user-name splunk_logserv_user \
  --access-key-id <access-key-id> --status Inactive
aws iam delete-access-key --user-name splunk_logserv_user --access-key-id <access-key-id>

# trust-policy.json now names only the instance profile role
aws iam update-assume-role-policy --role-name splunk-logserv-ta-role \
  --policy-document file://trust-policy.json

    The permissions policy the standard stack put on the IAM role works as it is. To narrow it to what the input uses, see What the Permissions Policy Leaves Out.

    Continue with step 5.


    Scenario C: Create or Reuse the IAM Role and Policy by Hand¶

    Three things must be true when you finish. Each sub-step shows how to get there with a new resource or with one you already have.

    What must be true Sub-step
    1 The IAM role’s trust policy lets the instance profile role assume it C.1
    2 The IAM role has a permissions policy (inline or customer managed) that reads SAP’s SQS queue and S3 bucket C.2
    3 The instance profile role may call sts:AssumeRole on the IAM role C.3

    The role name. SAP’s example policies show the name splunk-logserv-ta-role, and this page uses it. If you reuse an IAM role with another name, use that name wherever this page says splunk-logserv-ta-role, and give SAP that role’s ARN in step 4.

    C.1 The IAM Role and Its Trust Policy¶

    To create a new IAM role: in the IAM console, click Roles, then Create role, choose Custom trust policy, paste the document below with the ARN from step 2, click Next, add no permissions yet, name the role splunk-logserv-ta-role and create it.

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::<secondary-account-id>:role/<instance-profile-role-name>"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}

    To reuse an existing IAM role: open the role, click the Trust relationships tab, then Edit trust policy. Keep the statements that are there, and add the statement above to the Statement list (or add the ARN to the Principal of a statement that already allows sts:AssumeRole with no conditions). Click Update policy.

    Do not add an sts:ExternalId condition: the add-on sends none. A condition on the role session name must allow splunk_ta_aws.

    AWS CLI

    Save the trust policy as trust-policy.json, then:

    # New IAM role
aws iam create-role --role-name splunk-logserv-ta-role \
  --assume-role-policy-document file://trust-policy.json

# Existing IAM role: read its trust policy, add the statement, write it back
aws iam get-role --role-name <existing-role-name> \
  --query 'Role.AssumeRolePolicyDocument' --output json
aws iam update-assume-role-policy --role-name <existing-role-name> \
  --policy-document file://trust-policy.json
    C.2 The Permissions Policy¶

    The IAM role needs these permissions, on SAP’s resources:

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadSapQueue",
      "Effect": "Allow",
      "Action": [
        "sqs:ReceiveMessage",
        "sqs:DeleteMessage",
        "sqs:ChangeMessageVisibility",
        "sqs:GetQueueAttributes"
      ],
      "Resource": "arn:aws:sqs:<region>:<sap-ecs-account-id>:<queue-name>"
    },
    {
      "Sid": "ReadSapObjects",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:GetObjectVersion"
      ],
      "Resource": "arn:aws:s3:::<bucket-name>/*"
    },
    {
      "Sid": "ListSapBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::<bucket-name>"
    }
  ]
}

    If SAP uses a customer managed KMS key, add the kms:Decrypt statement from Customer Managed KMS Keys. s3:ListBucket is for AWS S3 Direct, which loads history; the SQS-Based S3 input does not use it.

    Pick one way to give them to the role:

    You have Do this in the IAM console
    A customer managed policy you want to reuse Open the policy and check on its Permissions tab that it allows every action above on SAP’s queue ARN and bucket. If it does not, click Edit and add what is missing. Then open the IAM role, click Add permissions > Attach policies, select the policy and click Add permissions
    No policy, and you want a customer managed policy (one policy you can attach to several roles and version) Click Policies, then Create policy, choose JSON, paste the document above with SAP’s values, name it splunk-logserv-ta-policy and create it. Then attach it to the IAM role as in the row above
    No policy, and an inline policy is enough (what the CloudFormation template does) Open the IAM role, click Add permissions > Create inline policy, choose JSON, paste the document above with SAP’s values, and name it splunk-logserv-ta-policy
    AWS CLI

    Save the permissions document as permissions-policy.json, then use one of these:

    # Reuse a customer managed policy: read its default version, then attach it
aws iam get-policy --policy-arn arn:aws:iam::<secondary-account-id>:policy/<policy-name> \
  --query 'Policy.DefaultVersionId' --output text
aws iam get-policy-version \
  --policy-arn arn:aws:iam::<secondary-account-id>:policy/<policy-name> \
  --version-id <version-id> --query 'PolicyVersion.Document' --output json
aws iam attach-role-policy --role-name splunk-logserv-ta-role \
  --policy-arn arn:aws:iam::<secondary-account-id>:policy/<policy-name>

# Add missing permissions to that policy: a new default version
aws iam create-policy-version \
  --policy-arn arn:aws:iam::<secondary-account-id>:policy/<policy-name> \
  --policy-document file://permissions-policy.json --set-as-default

# Create a new customer managed policy, then attach it
aws iam create-policy --policy-name splunk-logserv-ta-policy \
  --policy-document file://permissions-policy.json
aws iam attach-role-policy --role-name splunk-logserv-ta-role \
  --policy-arn arn:aws:iam::<secondary-account-id>:policy/splunk-logserv-ta-policy

# Or an inline policy on the IAM role
aws iam put-role-policy --role-name splunk-logserv-ta-role \
  --policy-name splunk-logserv-ta-policy --policy-document file://permissions-policy.json
    C.3 Allow the Instance Profile Role to Assume the IAM Role¶

    Open the instance profile role from step 2 in the IAM console, click Add permissions > Create inline policy, choose JSON, paste this with the ARN of splunk-logserv-ta-role, and name it splunk-logserv-sqs-based-input-assume-role-policy:

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::<secondary-account-id>:role/splunk-logserv-ta-role"
    }
  ]
}

    If you manage the instance profile role’s permissions in a customer managed policy of your own, add this statement to that policy instead.

    AWS requires this statement when the instance profile role is in a different AWS account from splunk-logserv-ta-role; add it in that account. In the same account the trust policy alone is enough, and the statement records what the instance profile role may assume.

    AWS CLI

    Save the document as assume-role-policy.json, then:

    aws iam put-role-policy --role-name <instance-profile-role-name> \
  --policy-name splunk-logserv-sqs-based-input-assume-role-policy \
  --policy-document file://assume-role-policy.json

    Continue with step 4, or with step B.4 if you came here from scenario B.


    4. Give SAP the IAM Role ARN¶

    Scenario B: skip this step. SAP’s policies already name the IAM role.

    4.a Copy the ARN of splunk-logserv-ta-role from its page in the IAM console (scenario A: the stack output SplunkLogServRoleArn). It looks like arn:aws:iam::<secondary-account-id>:role/splunk-logserv-ta-role. Do not send the ARN of the instance profile or of the instance profile role.

    4.b Ask SAP LogServ Support to add that ARN to the SQS queue access policy and the S3 bucket policy, keeping s3:ListBucket on the bucket as the example does. What to Ask SAP lists what else to confirm in the same request.

    Wait until SAP LogServ Support confirms that both policies are applied before step 7. Steps 5 and 6 can be done in the meantime.


    5. Confirm the Account in the Add-on¶

    Do steps 5 to 8 on each heavy forwarder that will run the input.

    5.a Log in to Splunk Web on the heavy forwarder with a Splunk admin role, open the Splunk Add-on for AWS, then click Configuration, then Account.

    5.b Look for a row named after the instance profile role, with Yes in the Autodiscovered IAM Role column. You do not add this account, and no key is stored. If the row is missing, see Troubleshooting.


    6. Add the IAM Role in the Add-on¶

    Scenario B: skip this step. The add-on already has the IAM role.

    6.a Click the IAM Role tab, then Add.

    6.b Enter a name that uses only letters, digits and underscores, for example splunk_logserv_ta_role, and the ARN of splunk-logserv-ta-role in IAM Role ARN, then click Add. Step 6 of the main guide has screenshots of this form.


    7. Test Access¶

    When you save an input, the add-on checks only the SQS queue. A missing S3 or KMS permission shows up only after the input has started taking messages. So test both from the heavy forwarder first: follow Test Access from the Heavy Forwarder. It needs AWS CLI v2 on the heavy forwarder, only reads, and takes a few minutes.


    8. Create or Switch the SQS-Based S3 Input¶

    Scenarios A and C: Create the Input¶

    The input starts with every notification already waiting in SAP’s SQS queue, up to 14 days of them. Read First Start: The Queue Backlog before you add it.

    8.a Click the Inputs tab, then Create New Input, Custom Data Type, then SQS-Based S3 (Recommended). Step 7 of the main guide has screenshots of this form.

    8.b Fill in the form:

    Field Value
    Name A descriptive name
    AWS Account The account named after the instance profile role (step 5)
    Assume Role The IAM role from step 6. It must not be the same role as the one in AWS Account
    Force using DLQ (Recommended) Checked
    AWS Region The Region of SAP’s queue
    Use Private Endpoints Unchecked
    SQS Queue Name Type the queue URL and select it as (New value): https://sqs.<region>.amazonaws.com/<sap-ecs-account-id>/<queue-name>. The dropdown cannot list a queue in another AWS account
    SQS Batch Size 10
    S3 File Decoder Custom Logs
    Signature Validate All Events Unchecked
    Source Type sap_logserv_logs
    Index sap_logserv_logs, or the name you gave the LogServ data index

    8.c Click Add, then disable the new input on the Inputs tab straight away.

    8.d Add the cloud attribution. In $SPLUNK_HOME/etc/apps/Splunk_TA_aws/local/inputs.conf, add this line to the input’s stanza, [aws_sqs_based_s3://<input name>]:

    _meta = cloud_provider::aws

    8.e Restart Splunk, then enable the input. Add the _meta Line to an AWS Input shows how to write the line over REST with no restart.

    Scenario B: Switch Your Existing Inputs¶

    8.f On the Inputs tab, edit each SQS-Based S3 input that uses the IAM user’s account. Change AWS Account to the account named after the instance profile role (step 5), leave Assume Role and every other field as they are, and save the input.

    8.g Check that the _meta = cloud_provider::aws line is still in each input’s stanza in $SPLUNK_HOME/etc/apps/Splunk_TA_aws/local/inputs.conf. Put it back if the edit removed it (step 8.d).

    8.h After step 9, go back to B.5 and retire the access key.


    9. Confirm LogServ Logs are Being Ingested¶

    Allow 5-10 minutes for the first events.

    9.a On a search head that can search the LogServ data index, run:

    index=sap_logserv_logs earliest=-1h | stats count by sourcetype, host

    You should see the sourcetypes your SAP LogServ subscription delivers, from several hosts. Verify Your Data has the full set of checks.

    9.b Check the add-on’s logs even if events arrive, because a permission problem on some objects does not stop the others:

    index=_internal source=*aws* level IN (ERROR,WARNING) earliest=-1h | head 50


    Troubleshooting¶

    What you see What to do
    No autodiscovered account under Configuration > Account The instance has no instance profile, or the Splunk user cannot reach the instance metadata service. Run the check in Heavy Forwarder Requirements
    Saving the input says The SQS Queue entered may not be present in the given region. The add-on shows this for any failure of its queue check: the trust policy does not name the instance profile role, SAP’s SQS queue access policy is not applied yet, or the Region or URL is wrong. Run step 7; its error names the failing call
    Saving the input says An error occurred (AccessDenied) when calling the AssumeRole operation: User: arn:aws:sts::<account-id>:assumed-role/<role-name>/<instance-id> is not authorized to perform: sts:AssumeRole on resource: arn:aws:iam::<account-id>:role/<role-name>, with the same role name in both places The role attached to the heavy forwarder instance is also the role selected in Assume Role, so it is asked to assume itself. Either attach a separate instance profile role to the instance (step 2) and let it assume this role (step 3), which is the setup this page describes; or, if the attached role already holds the permissions of C.2 and is the role SAP’s policies name, edit the input and clear Assume Role. The second way has not been run in our lab
    The SQS Queue Name dropdown is empty Expected. Type the queue URL (step 8.b)
    The input logs AccessDenied Disable the input at once, so that failed messages do not pile up or move to SAP’s dead-letter queue. Run step 7 and fix what it shows
    The input logs No AWS account named The instance profile on the instance changed. Restore it, or edit each input to the new account name and add the new instance profile role to the trust policy
