    Release Notes: 0.1.2¶

    This page lists what changed in each 0.1.2 build of the Splunk for SAP LogServ packages, newest first for each package. Read it before you upgrade, to see what a build changes and whom it affects; the steps an upgrade needs are in Upgrading to This Release. Earlier versions have their own pages: 0.1.1, 0.0.6 and 0.0.5 and earlier.

    Current Builds and How to Read Yours¶

    Data TA Splunk TA for SAP LogServ splunk_ta_sap_logserv 1792598960
    LogServ Azure add-on Splunk TA for SAP LogServ on Azure splunk_ta_sap_logserv_azure 1792558069
    LogServ GCP add-on Splunk TA for SAP LogServ on GCP splunk_ta_sap_logserv_gcp 1792558072

    All four packages are version 0.1.2, so within 0.1.2 only the build number tells two builds of a package apart.

    • The LogServ App numbers its builds in sequence. The App and build pills in its header show the version and build, and About, at the bottom of the left navigation rail, shows the version, the build and the build date.
    • The Data TA and the Azure and GCP add-ons are built with Splunk’s UCC framework, whose build number is the time the package was built, in Unix seconds (UTC): build 1792598960 was built on 2026-10-21 at 16:09 UTC. A higher number is a later build. Their entries below give the date as well as the build.

    To read the installed build of each package, run this search in Splunk Web on the instance you check (the search head for the App; each heavy forwarder, or the single instance, for the add-ons), or read build in the package’s default/app.conf as Version Check shows:

    | rest /services/apps/local splunk_server=local
| search title=splunk_app_sap_logserv OR title=splunk_ta_sap_logserv*
| table title version build

    Some builds were made only for testing and never released. From build 380 on, the entry of such a build is merged with the released build that carried its changes, as in builds 387–388. Earlier test builds of the App (361, 364, 372 and 374) keep their entries, each marked as not released. The App builds released since build 379 are 383, 385, 386, 388, 390, 392, 393 and 394.

    Each entry says what changed, who is affected and what an upgrade needs; Upgrading to This Release lists every action by the build you are coming from. A statement that a later build changed carries Superseded by build N, and a statement found to be wrong carries a Correction.

    v0.1.2 is the active line and carries everything in Release Notes: 0.1.1: the dashboard-performance data layer (tstats and KV Store rollups, the backfill panel, staggered schedules), the Azure and GCP ingest add-ons, the LogServ Data Doctor, the Environment Topology work and the LLM-driven AI Assistant.     LogServ App (splunk_app_sap_logserv)¶

    Builds of the Splunk App for SAP LogServ, which runs on the search head.

    The Audit Log’s user filter shows each name once (build 394)¶

    • With User contains set, Settings → AI Assistant → Audit Log showed each name twice in the User column (for example adminadmin). The filter makes Splunk extract user from the event to apply it, and the viewer’s spath then added the same value again. The viewer now reads user from the event’s JSON after spath, as it already did for category, so the column shows the name once with or without the filter.

    Who is affected: admins who read the Audit Log (Settings → AI Assistant → Audit Log) with User contains set.

    Upgrade action: none. No acknowledgement is asked again: the legal texts and their versions are unchanged.

    A newer Splunk MCP Server is no longer refused (build 393)¶

    • The AI Assistant no longer refuses a newer Splunk MCP Server. It used to refuse a version at or above an upper bound it had not been tested against (v3.0.0 since build 335), replacing the chat with an Uncertified version card. That bound is gone; the v1.0.3 security floor (CVE-2026-20205) stays, and the predefined prompts need v1.1.0 or later, the first version with the Run Saved Search tool they run through. A version reported in two parts, such as 3.0, now reads as 3.0.0; it used to be refused as too old. The newest version verified is 2.0.0 (the handshake, tools/list and tools/call); if a later version changed the protocol the AI Assistant depends on, that would show as failing tool calls in the chat rather than as a refusal to start.

    Who is affected: deployments whose Splunk MCP Server is version 3.0.0 or later, or reports its version in two parts.

    Upgrade action: none. No acknowledgement is asked again: the legal texts and their versions are unchanged.

    Audit events go where the settings in place when they were posted send them, and the dialog names both providers (builds 391–392)¶

    • The audit-forwarding acknowledgement’s audit event is posted as soon as the answer is recorded, for a Yes as for a No. A Yes’s event used to wait for the save, so a Yes followed by a failed save could leave the Yes recorded with no audit event, and the retry did not always ask again.
    • An audit event posted on its own goes where the audit settings in place at that moment send it. That covers the Settings page’s acknowledgement events, which are posted just before the save. Until now the forwarder setting was read only after the event’s local write, so that save could decide, while the event was being written, whether the event was also sent to the off-host forwarder. Now a Yes that turns forwarding off is also sent to the forwarder being turned off (an attempt with the forwarder settings the page has applied), and if that send fails, its failure record goes to the event’s audit index, even when the same save renames the index.
    • On a re-ask, the enablement dialog names the provider in effect, the one a No keeps; it named the provider selected on the page. When the same save also changes the LLM provider, it names both: the provider in effect, which a No keeps, and the one the save changes it to, which a Yes saves. When the AI Assistant is being turned on, it names the page’s provider.

    Build 391 was not released; its changes reached customers in build 392.

    Who is affected: admins who answer the AI Assistant’s acknowledgements in Settings, and whoever reviews the AI Assistant’s audit log.

    Upgrade action: none. No acknowledgement is asked again: the legal texts and their versions are unchanged.

    The Settings page waits for a No to be recorded, and the dialogs show their errors (builds 389–390)¶

    • The enablement dialog closes once a No has turned the AI Assistant off, before the No is recorded; until now it showed the turn-on wording and buttons for that moment. It also closes when an answer cannot be recorded, so the error shows on the page; it used to appear behind the dialog.
    • A No that turns the AI Assistant off keeps the Settings page busy until the No is recorded (the Save button reads Saving…); the page could be used again a moment too early.
    • The audit-forwarding dialog closes when its answer cannot be recorded, or when the save after a Yes fails, so the error shows on the page; it appeared behind the dialog.
    • A No’s audit event records the provider in effect, for both acknowledgements; it recorded the provider selected on the page, which a No does not save.

    Build 389 was not released; its changes reached customers in build 390.

    Who is affected: admins who answer the AI Assistant’s acknowledgements in Settings, and whoever reviews the AI Assistant’s audit log.

    Upgrade action: none. No acknowledgement is asked again: the legal texts and their versions are unchanged.

    Declining the AI Assistant terms turns the AI Assistant off, and the acknowledgements say where an answer is recorded (builds 387–388)¶

    • A No now does what the terms say. The enablement acknowledgement ends by saying that if Customer does not accept, the AI Assistant feature will remain disabled. That held when an admin was turning the AI Assistant on. When it was already on and the terms’ version rose, a No only cancelled that save: the AI Assistant stayed on, and the next save went through without asking. Now a No in that case turns the AI Assistant off. Only the Enable AI Assistant setting changes - nothing else in that save is applied - and it is written before the No is recorded, so if the write fails, the question is asked again at the next save. The dialog says so before the click, and its No button reads I do not accept (record No and turn off).
    • The enablement acknowledgement is at version 3. Two corrections raised it. Clause 7 said the administrator’s answer is recorded “via the standard Splunk telemetry endpoint”; the answer is recorded as an event in the AI Assistant audit log, with the administrator’s account name, network address and a timestamp, and, since build 240, stored with the acknowledged version in the KV Store, and the clause now says so. Its closing sentence now says the AI Assistant feature will then remain disabled or, if it is already enabled, be disabled. Turning the AI Assistant on asks every time, as before.
    • The note under both acknowledgements (outside their legal text) and the Settings page’s message when an answer cannot be recorded named the same telemetry endpoint. The note now names the audit log and the KV Store, and the message names the KV Store, the write that failed, without repeating itself.

    Build 387, which raised the enablement acknowledgement to version 2, was not released; its changes reached customers in build 388.

    Who is affected: deployments that run with the AI Assistant enabled.

    Upgrade action: nothing to rebuild. With the AI Assistant enabled, the next admin who saves the AI Assistant’s General settings (Save Defaults) is asked once to accept version 3 of the enablement acknowledgement; answering No turns the AI Assistant off. A local/ai_assistant_acks.conf that sets optInVersion under [logserv-ai-assistant-enable-tc] keeps the old version: remove that line. See Upgrading to This Release.

    The audit-log integrity acknowledgement names the audit index correctly (build 386)¶

    • The forwarder-disabled acknowledgement is at version 2. Its text named the audit index ai_assistant_audit, the index’s name before it was renamed logserv_ai_assistant_audit; it now reads the AI Assistant audit index (logserv_ai_assistant_audit, or the index set in Settings), so it stays correct where an admin named another index. Because the wording changed, its version rose from 1 to 2: on a deployment that runs with audit forwarding off, the next admin who saves the AI Assistant’s General settings (Save Defaults) is asked once to acknowledge the corrected text. With forwarding on nothing changes, and the AI Assistant enablement acknowledgement is unchanged.
    • Documentation. The add-ons’ urllib3 1.26.20 and the seven advisories scanners report against it are analysed in Third-Party Software Licenses: none affects the add-ons as shipped. The Application Settings page of this documentation now says an acknowledgement is recorded once per deployment.

    Who is affected: deployments that run with audit forwarding off.

    Upgrade action: nothing to rebuild. With audit forwarding off, the next admin who saves the AI Assistant’s General settings (Save Defaults) is asked once to acknowledge the corrected text. An optInVersion line under [logserv-ai-assistant-tc] in local/ai_assistant_acks.conf keeps the old version: remove it. See Upgrading to This Release.

    Dashboard data writable by admins only, and the audit warning names both capabilities Splunk accepts (builds 384–385)¶

    The App’s KV Store collections that hold dashboard data - the 24 rollups, the five Environment Topology collections and the Data Doctor’s platform snapshot - were writable by every role, so any signed-in user could alter or delete what the dashboards show through Splunk’s REST API. They are now writable by the admin, sc_admin and sc_subadmin roles only; every role can still read them. Their scheduled searches run as Splunk’s system user and the Settings → Dashboard Data backfill as the signed-in admin, so neither changes. Six collections stay writable by every role because ordinary users write them by design: the four per-user preferences (topology layouts, the default layout, the active layout mode, the dashboard refresh interval) and the Data Doctor’s saved reports and supplied ingest configuration.

    • Saved searches that write run as the requesting user. The 91 saved searches that write with outputlookup (the aggregate, backfill and retention searches of the rollups and topology collections, the Data Doctor’s platform-snapshot and report-retention searches, and the two ES feeds) now set dispatchAs = user. A user who starts one through Splunk’s REST API (saved/searches/<name>/dispatch) runs it with their own permissions, so a non-admin can no longer run a retention or a backfill that overwrites dashboard data. Their schedules run as before.
    • A stored refresh interval must be one the picker offers. The refresh-interval collection is writable by every role, so another user could store a one-second interval in your row and make every panel re-run each second; a stored value other than Never, 30s, 1m, 5m, 15m, 30m or 1hr is now ignored.
    • The Data Doctor says a supplier name is not verified. The name on a saved report and on a supplied ingest configuration is the one the browser sent, so the Data Doctor now shows it as (name not verified): the saved reports’ column reads By (not verified), and a re-downloaded saved report marks the name on its cover page, in the environment-fingerprint section’s Generated by, in the machine-readable appendix and in the JSON copy. The page’s note on saved reports no longer says every App collection is writable by every user. The platform snapshot’s provenance line now reads recorded by the hourly platform snapshot, a collection only Splunk administrators can write.
    • The AI Assistant’s audit warning names both capabilities. Splunk accepts the browser’s audit writes (receivers/simple) from a user who holds edit_tcp or edit_log_alert_event, and Splunk’s default power role holds edit_log_alert_event, so power users have been audited all along; only users whose sole role is user are refused. The warning (HTTP 403, or HTTP 401 after a reload) now names edit_log_alert_event, the narrower one to grant, and edit_tcp, and says Splunk’s default user role has neither; it no longer says power users lack them. See Audit Log.
    • The ingest-cutoff sentence gives the date first. The Data Doctor now says a range ends before the ingest cutoff of <date> (recorded as supplied by <name> (name not verified)), so the date no longer reads as the time the cutoff was supplied.
    • The Dashboard Data upgrade note names every panel a Backfill without the Clear inflates. Activity by SID / Instance on Work Process Performance counts the upgraded hours twice as well, and its WP Categories column counts each renamed component twice.

    Build 384 was not released; its changes reached customers in build 385.

    Who is affected: every deployment: non-admin users can no longer write the App’s dashboard data, and a scheduled search of your own that writes into one of these collections must be owned by an admin. Admins who read the AI Assistant’s audit warning (shown since build 383) now see both capabilities Splunk accepts.

It now catches each listed command at the start of the query and after a [ too, and adds collect’s aliases stash, summaryindex and sumindex; mcollect and meventcollect; outputtext, dump and createrss; runshellscript; rest (storage/passwords returns stored credentials decrypted); outputtelemetry and the third-party curl, wget and sendresults; the Machine Learning Toolkit’s ai (it sends the rows to an LLM) and deletemodel; and map and savedsearch’s aliases macro and savedsplunk.     • Tier 2 column names and time ranges no longer carry raw event text, and with PII redaction on a value is sent in clear only when the App can trace it to a field that is not an identifier. The Tier 2 summary used to send every column name, and the minimum and maximum of _time, exactly as the search returned them. Both can be data: timechart, chart, xyseries and transpose turn the values of a field — user or host names — into column names, eval {f}=… can turn any event text into a column name, timechart count by user | stats sum(*) makes sum(jsmith), and eval can set _time to any text. Now a column name is sent only when Splunk generates it (count, percent, NULL, OTHER, a bare function name such as avg, …) or when every word in it — each run of letters, digits and _, matched whole and in the same letter case — appears in the text the model or the App wrote for that call: the model’s own query (splunk_run_query), or the SPL of the App’s catalog search that ran. Text the model or the App wrote tells the vendor nothing new. Such a name must also be at most 40 characters and shaped like a field name or a single fn(field) call, or be a display alias the text quotes after AS (rename sourcetype AS "Source Type"; words separated by single spaces). Values now fail closed. With PII redaction on, a text column’s values are sent in clear only when the App can trace the column through constructs it reads in full — the field by its own name, a statistics function over one field (nested included), field AS alias, a rename without wildcards, lookup … OUTPUT x [AS y], eval y=x with one bare or single-quoted field, or a count — to fields that mark no identifier. Every other column sends every value as a <redacted-…> tag: any other eval expression (. concatenation, any function, a literal), rex, spath, strcat, a wildcard rename or AS, a dynamic eval {f}=… target, the cells of a pivot (timechart values(src_ip) by user), transpose, untable and fieldsummary, a column a subsearch defines, and every column after a command the App does not read in full; a text over 20,000 characters, more than 256 commands or subsearches nested more than 8 deep leave every column untraced. Until build 375 a value was redacted only when its column’s own name matched a pattern, so values(user), rename user AS u or eval w=user."@".domain sent user names in clear. A pure count (count, dc(user), dc(host) AS affected_hosts) keeps its numbers, and a numeric column sends values withheld only when it is not a count and its name or a field it reads marks an identifier, or it mixes many fields. The cost: with redaction on, the computed text columns of some of the App’s own catalog searches now arrive as tags — the error Category, the cross-stack stack, the Cloud Connector uri_prefix, the SAProuter peer, the HANA trace message_preview, the data-freshness last_seen and the threat-intel queries — while their counts are unchanged. With redaction on, a text column with an id-named source (user_id, employee_id, …) is redacted too, and a numeric one sends values withheld instead of its minimum and maximum. peer_ip, icm_peer_ip, a bare ip and peer are still not matched. The time range is sent only when every _time value is a timestamp, written by the App as ISO-8601 UTC and marked (UTC); otherwise it reads not shown. At most 30 columns are summarized. A single-valued numeric column whose name is withheld, or that is not a count and marks an identifier or mixes many fields, sends values withheld whatever the redaction setting. A search that returns no rows now reads Returned 0 rows in both tiers: Tier 1’s count is now the number of result rows, not the number of items in the content list of the MCP reply, so with the Splunk MCP Server it no longer reads Returned 1 rows whatever the search returned.     Firewall drops at the host and in transit (build 374)¶

    The kernel firewall log records two kinds of drop. IN_DROP is a packet addressed to the host itself (the INPUT chain). FWD_DROP is a packet the host was routing on to another system (the FORWARD chain); only hosts that forward traffic, such as VPN or IPsec gateways, log it. The Firewall Drops KPIs counted only IN_DROP, while the Blocked tables (Blocked Sources on Linux, Blocked Source IPs on Network Perimeter, and Blocked Destination Ports on both) already counted both, so a source could show more drops in a table than the KPI showed in total. On the reference instance FWD_DROP made up 92% of the real firewall drops.

    • Linux and Network Perimeter show Firewall Drops at Host and Firewall Drops in Transit side by side, and their Blocked tables split each row into At Host and In Transit / Other. Network Perimeter reads its in-transit count from the Linux dashboard’s summary data, so it shows 0, or undercounts, for any period the Linux rollup has not summarised: its aggregation turned off, or those days not backfilled.
    • Settings → Dashboard Data labels that rollup’s row Linux System & Security / Network Perimeter, naming both dashboards that read it, as it does the other shared rows; the Data TA’s AWS S3 Direct screen shows the same label (see the Data TA entry of 2026-10-01 below).
    • Linux’s Firewall Drops Over Time charts the two chains. It used to chart every linux_secure line, firewall or not.
    • Environment Health still counts only drops at the host as errors; its KPI, Security Error Trend series and Affected Hosts column now say so.
    • The AI Assistant’s two firewall prompts say which drops they count, and its system prompt names the real kernel tags, IN_DROP and FWD_DROP.

    Who is affected: deployments with Linux firewall logs, above all hosts that forward traffic, such as VPN or IPsec gateways.

    Data TA - six routing rules are tried once per event, not at every character (build 1791935359, 2026-10-13)¶

    Six of the Data TA’s sourcetype routes, for abap/audit, abap/sapstartsrv, hana/tracelogs, scc/audit, scc/tracelogs and sap/sapstartsrv, check two folder keys at once with a pattern such as (?=.*"clz_dir":"abap")(?=.*"clz_subdir":"audit"). Without a ^ at its start, the regex engine tries such a pattern again at every character of an event it does not match, and each try reads to the end of the first 4,096 characters, so the work for one event grows with the square of its length. Each route fails to match nearly every event, so the six ran this way on almost every LogServ event a heavy forwarder parsed. Splunk’s regex match limit counts the work of each start position on its own, so it never stopped these searches and nothing was logged.

    The six routes now start with (?s)^, so each is tried once per event. The (?s) keeps the routing as it was: in Splunk’s regular expressions . stops at a carriage return, vertical tab, form feed or a Unicode line or paragraph separator as well as at a line feed, and the forwarder ends an event only at a line feed or carriage return, so with a bare ^ such a character in the log text ahead of the folder keys would have left an event unrouted. With (?s)^ a route matches whenever both folder keys are in the event’s first 4,096 characters: it routes every event it routed before, no event in the real LogServ data checked changes sourcetype, the filter rules are not affected, and nothing has to be saved again after the update. On Splunk 9.4.3’s own regex library, measured at search time on generated LogServ events of 460 to 4,160 characters, anchoring made the six routes 179 to 1,778 times faster, with the same result for every event, and the (?s) costs nothing extra; the gain at index time on a forwarder is still to be measured. Every Data TA version from 0.0.4 on carries these routes. The change takes effect where the Data TA parses LogServ data, on the heavy forwarders or a single instance, once this build is installed there. To size heavy forwarders and measure the cost per event on your own, see Capacity Planning and First Start.

    Data TA — the Filters tab filters by source file, and its rules read the whole line (build 1791565776, 2026-10-09)¶

    The Configuration → Filters tab gains two fields, Include Sources and Exclude Sources. They match the event’s whole source value — the log file’s path, such as /var/log/zypper.log, or a name such as ps — with * for any run of characters (/ included) and ? for one character, case-sensitive; an entry can be limited to one folder, as in linux/linux_secure=/var/log/zypper.log. Exclude Sources drops log files that share a folder with a Primary log type without dropping the folder: zypper and YaST2 arrive in linux/linux_secure beside the firewall, kernel, sssd, lastlog and who logs (2.1 million /var/log/zypper.log lines in six weeks of real data on the reference system). Include Sources keeps files that an Include Filters allow-list would drop, including events that carry no folder fields at all — Unix command output such as ps and netstat, and HANA trace files, about 19.9 million real Azure events on the reference system. Both fields are empty by default, so nothing changes until you fill them in. Exclude Sources always wins, like Exclude Filters. See Configuring Filters for the order the rules apply in, and Filter Recipes for allow-list, deny-list and shared-folder settings.

    The existing filters are fixed in four ways:

    • Wildcards stay inside the value, whatever the Python version. The Data TA built its patterns with Python’s fnmatch, which let a * run past the end of the value into the rest of the line: linux/c*n also matched linux/cache whenever a later value in the line ended in n. The text it generated also differed between Python versions. A * now matches only within the value it stands in, and the generated text is the same on every Python version. Patterns with several * also run in linear time: each * but the last stops at the first place the text after it fits, so the work on a long value no longer multiplies with every *. What a pattern matches does not change.
    • Rules read the whole line. An index-time transform reads only the first 4,096 characters of a line unless told otherwise. In the AWS envelope the log text comes before the source, clz_dir and clz_subdir keys, so on a line whose log text ran past about 4,000 characters the folder keys were out of reach: an Include Filters allow-list dropped the line and an exclude missed it. Every generated filter stanza now sets LOOKAHEAD = 100000, the longest line the Data TA indexes, and the patterns skip over the log text, which keeps them within Splunk’s regex match limit on lines that long — raising LOOKAHEAD alone would have made the old patterns fail there.
    • The AWS S3 Direct screen’s filter preview matches the way the forwarder does. The screen leaves out folders the forwarder’s filters would drop, and it compared pattern text by prefix: with Filtering on and the default Include Filters */* it left out every folder, and a pattern such as */cron matched nothing. It now applies the same wildcard rules and the include-everything rule below, and, because a source rule acts on single files rather than folders, says where source rules may drop or keep some of a folder’s files.
    • */* or * anywhere in Include Filters keeps everything. Only */* or * on its own used to switch the include gate off; mixed with other entries, they did not.

    Behaviour change: an Include Filters value that mixes */* or a standalone * with other entries now keeps every event. Before, */*, linux/cron dropped every event without folder fields, and a standalone * beside other entries was ignored, so *, linux/cron kept only linux/cron — although the upgrade notification already treated both lists as covering every log type. To keep an allow-list, remove */* and * from it. With Filtering on, a save that sets Include Sources while Include Filters includes everything is refused, because the entries would have no effect.

After updating the Data TA, open Configuration → Filters, click Save, and on a Deployment Server click Deploy to Forwarders, so the forwarders get the regenerated rules. The upgrade notification still reads Include Filters only; source rules neither raise nor clear it.

The field’s help no longer shows how the screen names the inputs it creates, which read as a pattern for the job name itself. The Dashboards list shows the App’s labels for the two shared rows (see App build 369 above).

    Who is affected: users of the AWS S3 Direct screen.

    Upgrade action: none.

    Data TA — the filter paths real LogServ data uses (build 1790374045, 2026-09-25)¶

    The Data TA declares which folder paths each log type arrives under; the filter’s coverage warning, the App’s Data Doctor and the AWS S3 Direct screen all read that list. Checked against real deliveries, two layouts differ from it: the AWS bucket files Squid under proxy/squid, but Azure delivers it under linux/proxy; and GCP delivers the Pacemaker cluster log under linux/pacemaker and a proxy VM’s /var/log/messages under linux/proxy, where the list named only linux/slapd and linux/messages. The Data TA now declares both layouts — nothing that matched before stops matching, and routing is unchanged. With Filtering on and an include list that names only the older paths, the coverage warning now lists linux/pacemaker and linux/proxy, because events under them are dropped at the forwarder. The AWS S3 Direct screen reads both Squid folders and linux/pacemaker; a folder a bucket does not have gives an input that finds nothing.

    Who is affected: Azure and GCP deployments with Filtering on and an explicit include list.

    Upgrade action: with Filtering on and an explicit include list, add linux/proxy and linux/pacemaker where those logs should be kept; see Upgrading to This Release.

    Data TA — Squid’s cache and store logs get their own sourcetypes (build 1790374045, 2026-09-25)¶

    The Data TA gave all three Squid files the sourcetype squid:access, although only access.log holds requests: cache.log is the daemon’s own log and store.log the object-store journal. On the reference system the two made up 43% of the real feed’s proxy events, counted by any search that takes every squid:access event for a request, and tagged for the CIM Web data model. The Data TA now routes cache.log to squid:cache and store.log to squid:store; access.log stays squid:access. All three keep the proxy/squid filter path, so filter rules need no change and no upgrade warning appears. Events indexed before the update keep squid:access; the App’s proxy dashboards count access.log lines only and are correct either way. Saved searches of your own that read those two files under squid:access need the new names. On the reference system, real cache.log lines from the Azure feed arrive as squid:cache after the update, still carrying the splunk_solution and cloud_provider stamps and no automatic fields, while access.log lines stay squid:access.

    Who is affected: deployments with Squid proxy logs, and saved searches of your own that read cache.log or store.log under squid:access.

    Upgrade action: update those searches to squid:cache and squid:store; see Upgrading to This Release.

    Data TA — the S3 Direct scan checks find the add-on’s log (build 1790345882, 2026-09-25)¶

    Each backfill’s Did its inputs finish their scan? search, and the check for all backfills below the list, grouped the Splunk Add-on for AWS’s log lines by log_level. The add-on (8.1.0) writes level=, and stats … by drops every event whose group-by field is empty, so both searches returned no rows even for a backfill that had run. They now group by level, falling back to log_level and then to (none), so a line in any log format is counted. On the first real-data backfill — HANA audit logs for 2026-01-01 and 2026-01-02, 794 events — the old search returned nothing and the new one returns the input’s 187 log lines, all INFO.

    The troubleshooting search in the three AWS setup guides had the same flaw: log_level IN (ERROR,WARN) matched nothing, because the add-on writes level and names the warning level WARNING. It now reads level IN (ERROR,WARNING); on the reference system it finds 408 errors and 126 warnings over 30 days, where the old form found none. The step-by-step lists in those guides now render as lists; they had rendered as code blocks, bold markers and all.

    Who is affected: users of the AWS S3 Direct screen and of the AWS setup guides’ troubleshooting search.

    Upgrade action: none.

    Data TA — long NDJSON lines are unwrapped and kept whole (build 1790292318, 2026-09-24)¶

    Each LogServ line arrives wrapped in an NDJSON envelope, and the index-time transform [set_raw_only] keeps only its _raw string. On long lines carrying many escaped characters — from about 1.5 KB, common in some Azure-delivered logs — the transform’s regex exceeded Splunk’s PCRE depth limit, and the event was indexed with its envelope still on (about 400 events an hour on the affected forwarder). Lines longer than 10,000 bytes were also cut by the default TRUNCATE, which took their timestamp with them when _raw came before _time.

    [set_raw_only] now uses a possessive pattern that finds the same match at bounded depth; TRUNCATE = 100000 on [sap_logserv_logs] lets lines up to 100,000 bytes through whole; and LOOKAHEAD = 100000 on [set_raw_only] lets the transform reach the end of such a line — an index-time transform searches only the first 4,096 characters by default and misses a longer match silently. Since the fix the heavy forwarders log no regex errors and no truncations, no event arrives wrapped, and the longest line seen (about 52 KB) indexes whole. The fix applies to data parsed after the Data TA is updated on the heavy forwarders; events indexed earlier keep their envelope.

    Who is affected: deployments with long NDJSON lines, common in some Azure-delivered logs.

    Upgrade action: update the Data TA where LogServ data is parsed. With a Deployment Server, install it on the Deployment Server, replace its deployment-apps/ copy and click Deploy to Forwarders; do not install it directly on a forwarder that the Deployment Server manages, because the next push replaces that copy. See Updating the Data TA. Events indexed earlier keep their envelope.

    Data TA — AWS S3 Direct backfills by dashboard (build 1790292318, 2026-09-24)¶

    The AWS S3 Direct screen no longer asks for a key prefix. You pick the Dashboard Data rows to backfill — the same 25 rows as the App’s Settings → Dashboard Data — and Scan from / Scan until as UTC dates, inclusive and at most 366 days apart. The dates select the date folders in the S3 key, not the objects’ upload time. The screen creates one Generic S3 input per folder and year, limited to the chosen days and set to stop by itself 24 hours after it is created; it skips days its own earlier backfills already cover, and it leaves out folders or days the TA’s filters would discard on arrival, saying why. The list groups the inputs by backfill job, with Enable all, Disable all and Delete all, and two searches per job: one shows whether its inputs scanned, the other counts the events they indexed. After creating a backfill, backfill the same rows and dates in the App so the dashboards pick the events up. Prefer Disable to Delete: a deleted backfill no longer counts as covering its days.

    Inputs created here are stamped cloud_provider = aws through the Data TA’s own endpoint, /services/splunk_ta_sap_logserv/s3_direct_meta — POST only, run as the signed-in user, and limited to the inputs this screen names. Enable and Disable go through the add-on’s own endpoint. The Data TA published on 2026-09-20 made both calls to the add-on’s native data/inputs/aws_s3 endpoint, which Splunk Web does not pass through, so from the browser its Enable/Disable failed and no input was stamped. Tested with the Splunk Add-on for AWS 8.1.0. See AWS S3 Direct: Backfill and Recovery.

    Who is affected: users of the AWS S3 Direct screen.

    Upgrade action: none.

    AWS CloudFormation Templates (aws_assets/)¶

    Changes to the CloudFormation templates the AWS setup guides deploy.

    AWS templates - the Copy Lambda runs on Python 3.12, and the Lambda code bucket has no default (2026-10-23)¶

    • The Copy template’s Lambda runs on Python 3.12. splunk-logserv-remote-s3-copy.yaml created its forwarder function on python3.9, which AWS deprecated on 2025-12-15: AWS no longer applies security patches to it, and blocks creating python3.9 functions from 2027-07-29 and updating them from 2027-08-31. The template now uses python3.12, as the Filter template already did. The function’s code is unchanged.
    • LambdaCodeBucket has no default in the Filter and Copy templates. The default, splunk-logserv-lambda-binary, named a bucket that only one AWS account can own, because S3 bucket names are global. Create a bucket with a name of your own, in the Region of the stack, upload the Lambda ZIP file to it, and enter its name; CloudFormation now asks for it. See the Filter and Copy guides.

    Who is affected: customers who deploy the Filter or Copy template, and existing Copy stacks.

    Upgrade action: an existing Copy stack keeps python3.9 until you update it: update the stack with the current template and keep the existing parameter values. Against the previous template, the only resource change is the function’s runtime; its code and the bucket it is read from stay the same. Existing Filter and Copy stacks need no change for LambdaCodeBucket: a stack keeps the value it was created with.
