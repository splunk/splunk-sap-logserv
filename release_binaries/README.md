# v0.1.2 Release Binaries

This directory contains the **v0.1.2** release set: the four installable tarballs for **Splunk for SAP LogServ** — the Search-Head App (**the full-LLM build — free-form chat is available once a provider credential is configured**), the Data TA, and the per-Heavy-Forwarder Azure and GCP ingest add-ons — each beside its AppInspect report. Where this document says "canonical" without qualification it means v0.1.2. Every artifact carries version **0.1.2**; the App was last promoted on **2026-10-22** (App build **394**) and the Data TA and the Azure and GCP add-ons on **2026-10-21** (builds **1792598960**, **1792558069** and **1792558072**). The preceding **v0.1.1** set, kept here beside it from 2026-09-20, was removed from this directory on 2026-10-22; the v0.1.1 line is frozen, and the passages below that describe it are history.

**The canonical App artifact is the full-LLM build variant** (user direction, 2026-09-14 — reversing the 2026-08-18 templates-only decision): the App compiled with plain `yarn build`, in which the free-form LLM path is present and governed at run time by the **`templates_only_mode`** setting (default **false**). An admin can still restrict a deployment to canned prompts without rebuilding by turning that toggle on. The **templates-only build of the exact same source and build number** — whose compile-time flag forces the LLM path off at every config-read path (the build-300 gate: free-form chat disabled behind an explanatory banner, provider credentials and model discovery inert, the runtime toggle hidden) — is not shipped in this directory but is buildable from this source at any time with `yarn build:templates-only`; the two variants' bundles are byte-identical except the compiled flag module, the staged conf default and the styled-components build salt. The v0.1.1 **source** remains the LLM-capable line.

**v0.1.1 was the actively developed release line until it was frozen on 2026-09-18** (v0.1.2 is the active line). As of App build 245 (2026-07-05) it is at **full feature parity with v0.0.6** — the entire dashboard-performance data-layer rewrite (tstats + KV-Store rollups + the Settings → Dashboard Data backfill panel + staggered schedules), the Azure and GCP ingest add-ons, the three-way Multi-Cloud Overview, the Enterprise Security enable + re-stagger, and every AI Assistant fix (build-248/249 prompt repairs, the build-250 MCP time-range fix, the build-251 rollup-backed host prompts, the build-252 react-router 7.18.1 bump, the build-253 three-way Multi-Cloud dashboard) — while shipping the four vendor LLM providers (Anthropic / OpenAI / Azure OpenAI / AWS Bedrock), free-form chat, Power Mode, privacy tiers, and the Provider Credentials Settings tab. In the **full-LLM build variant** the runtime **`templates_only_mode`** toggle (default **false**) lets an admin restrict a deployment to canned prompts without rebuilding; in the templates-only variant shipped here that state is forced on at compile time and the toggle is hidden. The sibling **v0.0.6 line** (frozen) publishes the LLM-STRIPPED build of the same feature set — the providers physically absent from the bundle, versus this line's functional compile-time disable.

**Build 299 (2026-08-07) fixes the after-hours window, which was a silent no-op product-wide** (shipped to v0.0.6 as build 266). The `[sap:hana:audit]` props.conf calculated fields chained one EVAL onto another (`hour_of_day` derived from `EVAL-audit_datetime`), which Splunk does not reliably resolve — so `hour_of_day` and `day_of_week` measured **0% populated** and `is_business_hours` was pinned to the dead constant `"false"` on every event. Two opposite failure modes followed, decided purely by quoting. The HANA Audit **"After-Hours / Weekend Admin Activity"** panel compared against a bare `false`, which in a `where` clause parses as a *field reference*, so it matched nothing: the filter degenerated to weekend-only, **omitting every weekday after-hours event** (the security-relevant slice) and mislabelling all rows "Weekend". The Change & Configuration Activity **After-Hours Changes** KPI and its rollup used the quoted form, which matched the constant and flagged **100% of HANA events** as after-hours. Both are fixed: props.conf now derives each field inline from `_time`, and every consumer (the HANA panel, the ChangeConfig `ENRICH` classifier, and the `logserv_compliance_aggregate` / `_backfill` rollup arms) computes the window inline rather than reading a search-time field — an invisible dependency for a security filter that fails silently in both directions. One canonical window applies to all three change sources: **business hours 08:00–18:59, after-hours = hour < 8 OR hour > 18 OR weekend** (previously HANA delegated to the dead fields while Windows/Linux used a 07:00–19:59 window). Verified on 106M events: the corrected HANA panel query matches an independently-formulated reference exactly (980,650), recovering **540,185 weekday after-hours events** that were previously invisible, and the rebuilt rollup matches raw exactly on every source. Existing installs should re-run the compliance rollup backfill — `is_after_hours` is part of the rollup's `_key`, so historical rows carry the old classification. Two deliberate exceptions are documented and unchanged: the three ES off-hours correlation searches (`hour < 8 OR hour >= 18`) and the `logserv_hana_after_hours_admin` prompt (`hour < 6 OR hour >= 20`, a deep-overnight tripwire that states its own window).

**Build 300 (2026-08-07) makes `yarn build:templates-only` actually disable the LLM path.** The compile-time `TEMPLATES_ONLY` flag existed and was correctly wired (`bin/build.js --templates-only` → webpack DefinePlugin → `pages/home/buildFlags.ts`), but session 030 had moved the user-facing gating to the **runtime** `templates_only_mode` setting — so the flag only gated model discovery and two Settings rows, and a templates-only build still had **working free-form LLM chat**. The flag now *forces the runtime value on* at the config-read chokepoint (`utils/aiConfigApi.ts`): `parseRawContent` is the single normalizer for **both** storage sources (the KV-Store settings row and the conf-file stanza) and `DEFAULT_AI_CONFIG` is the both-reads-failed fallback, so every read path reports `templates_only_mode: true` regardless of what is stored — which the existing runtime machinery then acts on (chat input read-only, Send disabled, `sendUserMessage` short-circuits with a system notice, model picker + Power Mode hidden, Provider Credentials tab hidden, explanatory banner). Patching only the shipped conf default would **not** have been sufficient: **KV Store wins over the conf**, so a customer upgrading from a full-LLM build — whose KV row holds `templates_only_mode = 0`, exactly the state the test fleet is in — would have kept the LLM path enabled. Also forced: the pre-load default (`state/AIAssistantConfig.ts`), so the window before the async config read resolves cannot present an LLM-enabled UI, and the `sendUserMessage` guard itself (defense in depth, independent of the prop chain). The Settings **"Templates-only mode"** toggle is hidden in such a build — it could not turn the LLM path back on, so rendering it would be a control that lies — and `bin/build.js` patches the **staged** conf default to `true` (tolerant regex + self-assert that fails the build on formatting drift; the source conf is never touched) so the artifact is self-describing to `btool` / the REST conf endpoint. Per the standing decision the vendor provider modules are **not** stripped from the bundle: this is a functional disable, so vendor endpoint strings remain in `home.js`. **The full-LLM build is provably unchanged** — the two variants' `home.js` are the same length and differ in exactly two regions: the compiled flag module (`{F:()=>r});var r=!0` vs `var r=!1`) and styled-components' known per-build salt. The templates-only variant of this build is preserved in [`../testing/iteration_tarballs/`](../testing/iteration_tarballs/) as `splunk_app_sap_logserv-0.1.1-build300-templates-only.tar.gz` (md5 `650cd4e62564c22bbec17e0aa1271953`); it is a **build variant, not a separate canonical** — the canonical v0.1.1 App is and remains the full-LLM build.

### :material-circle-box: 2026-09-11 — the scan floor was a value Splunk rejects

The AWS S3 Direct screen's scan-window floor had been `1970-01-01T00:00:00Z` since the
screen was written. **Splunk's own time parser rejects every 1970 date.** Measured on
`splunk-hf-01`, `splunk-hf-02` and `splunk-sh-idxr` (all Splunk 9.4.3):

```
GET search/timeparser?time=1970-01-01T00:00:00Z  ->  HTTP 400 <msg type="FATAL">Invalid time.</msg>
GET search/timeparser?time=1971-01-01T00:00:00Z  ->  HTTP 200
```

That matters because the add-on validates this field **locally on create** but resolves it
**through that parser on every poll** (`aws_s3_conf.py::_get_last_modified_time` ->
`ta_aws_common.py::parse_datetime`). An input built on a 1970 floor therefore saved cleanly,
the screen reported *"Created — starts polling immediately"*, and the modinput then raised on
every poll into a broad `except` that logs one line: **zero events, forever** — and because
`buildUpdate` omits scan-from by design and the field is read-only on edit, it could not be
repaired from the screen. This is precisely the *reports success, fetches nothing* failure the
scan-window work exists to eliminate.

It had been masked rather than absent: the previous build defaulted the window to the current
calendar month, so the floor was reachable only by following the screen's own widening advice
(*"set the date to 1970-01-01 and the time to 00:00:00"*) or the documentation, which
recommended the same value in two more places, one of them the documented remedy for a blank
scan window.

**What changed**

- `SCAN_FLOOR` is now **`2000-01-01T00:00:00Z`** — below anything S3 can hold (S3 launched in
  2006) and clear of the parser's cliff, which is exactly epoch 31536000.
- The scan-from default reverts from the current calendar month to that floor. The two ends of
  the window are chosen for opposite reasons: scan-from **selects**, so the widest bound is the
  only one that cannot silently fetch nothing on a re-staged archive; scan-until still defaults
  to month end because that bound **terminates**.
- A client-side check refuses any scan date below the measured cliff, so the failure cannot be
  reproduced by typing either — fixing only the default would have left it one keystroke away
  in help text that invites widening.
- `index` is now required before a Save is offered. The vendor declares it `required=True`, so

### :material-circle-box: 2026-09-18 — the days_in_past guard could not fire where the screen pointed

The AWS S3 Direct screen blocks a key prefix whose events the forwarder's own

blind spot silenced the SQS-overlap warning for any prefix coarser than a single day.

**newest** instant the partition can contain. So:

- a `2025/` prefix wholly behind the cutoff now blocks, where it was previously accepted

- a year-wide prefix now raises the SQS double-ingest warning it could not raise before;
- a month out of range (`2025/13/`) and a day `Date.UTC` would roll into the next month
  (`2025/06/31/`) are refused rather than silently widened to a date the operator never
  wrote.

## Known third-party advisories

The Data TA and the Azure and GCP add-ons bundle urllib3 1.26.20,
which scanners report as affected by seven advisories (CVE-2025-50181, CVE-2025-66418, CVE-2025-66471,
CVE-2026-21441, CVE-2026-44431, CVE-2026-97687, CVE-2026-97689). Our analysis: none affects the add-ons as shipped.
urllib3 is used only for calls to the local splunkd management port, the add-ons' outbound connections use Python's
standard library, and urllib3 2.x cannot load in the Python of Splunk Enterprise 9.4 (OpenSSL 1.0.2). The analysis,
advisory by advisory, and the one configuration step (set `NO_PROXY=127.0.0.1,localhost` when splunkd runs with an
HTTPS proxy) are in the docs: [Third-Party Software Licenses](../docs/content/overview/third-party-licenses.md#known-advisories-urllib3-12620).
